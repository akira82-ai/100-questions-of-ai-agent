# Chapter 6 · Boundaries, Alternatives, and Future Judgment

## 87. Why should complex backend systems and formal production development not be rashly handed to it just because it can also do web pages and code?

Being able to generate code and being able to bear production-level responsibility are two different things. Making web pages, writing scripts, building local small tools, it can indeed get started, especially fit for validating ideas, making prototypes, handling personal efficiency tools. But complex backend systems involve another set of requirements: stability under high concurrency, data consistency, permission audit, failure rollback, long-term maintainability. In these scenarios, the cost of one wrong line of code may be an online incident. The docs are also restrained on zero-code local apps, suggesting first make the minimum viable version and finish core functions before expanding, which itself shows it fits exploration and validation, not replacing the formal engineering chain. Using it to quickly try out a prototype, then handing to formal development to harden and launch, is a more reasonable division. Treating it as a prototype accelerator is valuable; treating it as a production substitute is risky.

## 88. What tasks fit staying in WorkBuddy, and what tasks should switch to a more specialized way?

Staying in WorkBuddy are office tasks that need reading, processing, and generating strung into one chain. Its strength is catching a whole workflow: read files, understand content, call tools, produce deliverable results. Weekly report generation, meeting note extraction, data visualization, batch file organizing, material to web page, all fit well. What should switch to specialized ways are links with extremely clear boundaries and already-mature professional tools, such as complex financial modeling, formal code engineering, precise chart design; the depth and precision of specialized tools far exceed a general Agent. The criterion is simple: does this thing need multiple steps, multiple formats, coordination across reading and writing. If yes, stay here; if it is just a single link's deep operation, a specialized tool is handier.

## 89. In what scenarios does manual processing remain more direct and more stable?

Scenarios where judgment highly depends on on-site experience and needs flexible adjustment at any time are more stable done manually. Such as adapting live during a client negotiation, aesthetic judgment of a design draft, weighing complex personnel issues; the value of these lies in the person's immediate perception and trade-offs, not execution speed. The benefit of manual is you can adjust anytime by the other side's reaction, and fold ineffable judgment into every decision. WorkBuddy is good at efficiently executing clearly defined things, but tasks whose definition is vague and need deciding while doing, handing to it costs more time repeatedly aligning. Another class also fits manual: very small, one-time tasks not worth building a process. To configure a Connector, write a prompt, set automation for a one-time thing, the cost cannot be recovered.

## 90. Why are not all materials and directories worth throwing at WorkBuddy wholesale?

Because some things thrown out often bring risk and chaos, not efficiency. One class is sensitive materials, files involving client privacy, contract details, personal info; putting them into an Agent that reads, processes, and may send out via Connector, with boundary uncontrolled, is an incident. One class is extremely messy directories whose content you yourself cannot clarify, such as a desktop piled with temp files; handing it over equals letting it guess what is relevant among noise, and wrong guesses mean more reading and acting. The docs also specifically remind not to hand the whole desktop to it; giving it a dedicated directory is safer. To judge whether to hand over, ask: does the time saved by handing this out outweigh the risk of it reading, editing, sending wrong. If yes, hand; if no, keep in hand.

## 91. Why does boundary management become more important as Connectors and platform access multiply?

Each extra Connector adds a layer of materials it can see and systems it can touch; these capabilities stack. With one or two, you still know clearly what it can touch; after connecting seven or eight email, docs, cloud drive, message platforms, you yourself may not remember all. Boundary management becomes critical at this stage because it directly decides whether you can trust it to act. The safety tips in the docs all point to one thing: Connectors need corresponding permissions, can be disabled or disconnected anytime after authorization, and periodic Connector status checks are suggested. Good boundary management has a few moves: authorize only permissions the current task needs, turn off when done, periodically inventory which services are still connected, keep high-consequence actions at the human-confirmation layer. Access is capability expansion; boundary management is the brake that keeps this expansion from losing control.

## 92. After local workbench, Remote Assistant, and platform access are put together, what management cost really gets heavy?

It is boundary maintenance and state confirmation themselves. Each item alone is not complex: local workbench executes, Remote Assistant lets you instruct away from the computer, platform access brings external services in. But after the three stack, what you manage multiplies: which Connectors are still connected, which computer is online, which Workspace is current, which automation should run, whether the push really reached the mini-program. These are not one-time configs; they need continuous watching. The reminders recurring in the docs, such as computer must stay on and running, network must be normal, Connectors must be checked periodically, automation must be managed in the Workspace, all say the same thing: this system can run, but you must maintain its running environment. The more complete the capability, the wider the maintenance surface. The truly heavy cost is not learning features, but continuously ensuring all this stays in the correct state.

## 93. As models multiply, how do you avoid treating model switching as the only solution?

Switching models is indeed a common means; the docs, when meeting unreadable files, stuck tasks, abnormal output, first suggest switching the model to test. But if every problem only relies on switching models, you miss what should really be fixed. Some problems switching models eases, such as a model not supporting a file type; some problems switching models cannot cure, such as the task itself too broad, directory not set right, fuzzy points in the need it cannot understand; the latter will still stick at the same place no matter how many models you switch. A more stable habit: when a problem appears, first switch the model to try once; if unsolved, go back to check process and need. Classifying error codes, locating the stuck step, writing the fuzzy need clearly, these moves are more useful than mindlessly switching models. The model is a tool variable, not a universal switch.

## 94. As Skills, MCP, and Connectors all expand, which authorization boundary should ordinary users hold first?

Hold the line of what it can do externally first. Skills more affect internal execution style; turning off at most means a capability not called, limited impact. MCP and Connectors are different; they directly decide how far WorkBuddy's hand can reach into external systems: whether it can read your email, write your cloud drive, send messages to the work group, touch your online docs. Once these actions execute, the consequence is outward and hard to undo. The docs split permission into default and full access; under default permission, sensitive operations and execution outside the Workspace both need your confirmation; this setting is the safety net for ordinary users. When expanding capability, hold this boundary first: Connectors only authorize the scope the current task needs, turn off when done, periodically inventory what is still connected, outward-send actions always leave human confirmation. Skills can be installed more to try; MCP and Connectors must be connected with caution. Tinker internally, restrain externally.

## 95. Why does what really widens the gap often turn out to be task structure and acceptance method, not the prompt?

Because however refined the prompt, it is only the input of a single task; task structure and acceptance method decide whether you can stably reuse and keep getting reliable results. Many spend energy pondering how to write one sentence better, but never think clearly how many steps this task has, what each step's input and output is, what standard to accept at the end; the result is occasionally written well, but drifts with a different material. Those who really widen the gap care about two deeper layers: is the task structure clear, can it be broken into acceptable links; is the acceptance method hard, looking at the file itself or at its says completed. The docs repeatedly stress verifiable results, verify before expanding, check the four result-area views, all speaking of this acceptance layer. The prompt is technique; task structure and acceptance are the principle. Think the latter two clearly, and even with a plainer prompt, the result is more stable.

## 96. In what case does WorkBuddy go from one-time trial to a workbench you fixedly open?

It happens after you cross that threshold: find a high-frequency reusable, already-smooth scenario you can run as-is next time. The one-time trial state is you occasionally remember it, throw a task to try, close after done, and next time still reorganize. The fixedly-open state is you open it by habit before starting work, because you know a few jobs are easier handed to it, and these jobs' processes are already stable. The docs describe exactly this shift: from occasional use to opening daily, what gets stuck in between is whether there is a stably reusable scenario. This scenario usually has a few traits: high frequency, fixed rules, acceptable deliverable, verified more than once. Trial relies on novelty; workbench relies on real time saved. The latter is the reason it can stay in your daily work long-term.

## 97. Should you hand it outward-send, formal publish, direct file-edit actions or not?

You can hand it the preparation, but the last move is still better done by a human. The common point of these actions is outward consequence, hard to undo. Email to wrong recipient, document published with uncleaned content, directly overwriting important original files, these troubles are not solved by internal rework. It is very fit to help you finish the front work: draft email, organize document, prepare the version to edit. But at the moment of real send, publish, overwrite, one more human confirmation costs little and saves high risk. The docs, when talking about Connectors and assistants, also imply this: under default permission sensitive operations need confirmation, authorization can be turned off anytime. Separate high-consequence actions from the high-efficiency process: let it run the front, efficiency is its; the last nod is yours, responsibility is yours.

## 98. Why does many features not meaning you should use them all at the start?

Many features only mean more possibilities, not that each fits your current scenario. Throwing models, Experts, Skills, Connectors, automation, Remote Assistant all out at once, the result is often none used thoroughly, plus higher mutual-interference probability. The docs specifically remind to enable only the Skills the current task needs, reducing irrelevant interference and mis-calls; this principle holds on the whole feature surface too. A more stable rhythm is to start from one concrete scenario, run it smooth, stable, habitual, then consider adding the next capability; each layer added verifies it truly saves you effort, not makes you busier. Features serve you, not for collecting. Using three features thoroughly builds more real judgment than shallowly tasting ten. Fewer but accurate always beats all but messy.

## 99. If you only plan to learn part first, which basic capabilities should you hold first?

Hold three most. One, stating needs: able to say clearly what to do, what materials, what result; this is the base of all later capability. Two, accepting via the result area: know to open the artifact, all-files, change, preview four views to check what it actually delivered, not just look at the says completed in the chat. Three, controlling boundaries: know to give it a dedicated directory not the whole desktop, know to leave sensitive operations to human confirmation, know to preview high-risk actions before executing. These three together let you stably use it on real work. How to pick models, pull Experts, connect Connectors, build automation, these are advanced; can be added slowly later. Without holding these three basics, however fancy the advanced features, the result drifts.

## 100. What misuse and misjudgment should these 100 questions ultimately help you avoid?

Help you avoid three most damaging misjudgments. The first is using it as a chat box, only asking not delivering, forever stuck at its shallowest layer, then concluding it is just so-so. The second is using it as a universal substitute, handing full authority at once, letting it auto-send, overwrite originals, organize the whole desktop, then executing very seriously on a wrong premise, causing trouble it should not. The third is frequently switching the base as the only solution, switching models, adding Skills, connecting Connectors, but not going back to check process and acceptance, so the same pit is stepped repeatedly. These 100 questions keep saying the same thing: the key to using it is not many features, but clear task structure, controllable boundaries, hard acceptance. Avoid these three misjudgments and you will not miss it in scenarios where it truly helps, nor blindly trust it where it should not be let go. The value of a tool ultimately depends on whether its user knows where its boundary is.
