# Chapter 5 · Real Office Workflows and Scenarios

## 71. For the first try, why is the Excel to weekly report to PPT loop most recommended?

Because this chain strings together exactly its core capabilities, and each step is acceptable. The start is Excel; you have ready data, let it count by month, generate bar and line charts, testing reading and visualization. The middle is the weekly report, processing data into conclusions, testing induction and writing. The end is PPT, organizing content into a presentation, testing structuring and layout. Three steps progress; the previous step's product is exactly the next step's input, and all are files you can directly open and use. This loop has almost no vague space; after one run you know its real level.

## 72. How do you turn a pile of meeting notes into a truly accountable to-do list?

The key to accountability is that each to-do binds to a person and a time. Many organize notes and end up with a summary of what everyone discussed, which cannot be held accountable because it has no action items. A truly accountable list needs at least three blocks: the conclusion of each topic, the responsible person, the deadline. Put the requirement directly into the instruction, such as organize into a list with the conclusion, responsible person, and deadline of each topic, mark disputed and unresolved items, output as a table, no preamble. Limiting output to a table forces it to break each item into structured fields. Do not forget to mark disputed and unresolved separately; these are exactly the points most easily argued later.

## 73. Why is a material to web page task good for testing whether WorkBuddy can truly deliver?

Because a web page is a complete, openable, interactive product that cannot be faked with a paragraph of text. You ask it to turn materials into a web page, and it must truly organize structure, lay out pages, handle styles, and finally run. The preview view in the result area shows the effect directly; without downloading you can confirm structure, style, and interaction. Passing this gate means it delivers real things; failing, you see at a glance. Compared with Word or Excel, a web page tests can it be used harder: Word has large fault tolerance, can hand in even missing a section, but a web page that does not open or has messy structure simply fails. To quickly find its delivery bottom line, try a material-to-web-page task once; it is far more accurate than repeatedly asking what can you do.

## 74. How do you let it make a web page with previewable results without complicating things?

Let it run the minimum runnable version first, then add things round by round. The first time, do not ask for complex interaction, multiple pages, or fine styles; first generate a version with core functions running, such as a simple tool supporting add, search, edit. After generating, look directly in the result-area preview, confirm the basic structure is fine, then keep iterating in conversation, adding only one class of capability at a time. The docs suggest this too: first make the minimum viable version, split upgrade needs apart, add only one class of capability at a time. The preview view lets you see whether the page changed right without opening external tools each time. Small steps fast beat piling everything at once.

## 75. How do you use a Connector to turn Tencent Docs content directly into a deliverable?

Connect the Connector first, then issue the task; the whole process needs no local download. Tencent Docs is one of the Connectors built into WorkBuddy; once connected it can directly read your online document content and process by your requirements. For example, ask it to read this project weekly report in Tencent Docs, organize key progress, risks, and next-week plan, generate a Word stored in the weekly report directory. The Connector saves the download, organize, re-upload steps; you just issue tasks around the online material. The docs remind that Connectors need corresponding permissions, grant them correctly, and they can be disabled or disconnected anytime after authorization. Before connecting, confirm permissions are enough; after connecting, first use a simple read task to verify the chain works, then do complex processing.

## 76. Why is email summary more suitable as the first loop than auto-send email?

Email summary is low risk, auto-send email is high risk; the first loop should pick the most stable. Email summary only lets it read, organize, and distill email content for you to see, with no external action throughout; even if understanding drifts, the worst is a not-good-enough summary, just redo once. Auto-send email, once sent, with wrong recipient, wrong content, or bad wording, cannot be undone in time. The docs, when talking about the daily brief, also clearly suggest manually executing once first to confirm content, process, and receipt are normal, then enable automation. The logic behind this order is: verify the chain first, then release permission. Once the summary line is stable, consider the outward send step.

## 77. How do you make batch renaming both time-saving and not easy to lose files?

The core is preview first, execute later, with a confirmation gate in between. The easiest place for batch renaming to go wrong is that it changes a bunch of file names at once; by the time you find the rule is wrong, it is already done, hard to restore one by one. So the first step is to let it show the rename preview result: what the old name is, what the new name is, listed for you to see, then really execute after confirmation. The example instruction in the docs is exactly this idea: read file content or attributes, batch rename by date plus theme plus type rule, and show the rename preview result first. Another safe practice is to try a small sample batch first, verify the rule meets expectation, then expand to full volume. The rule should be written as a hard condition, not a soft rule like classify by importance that it can only guess.

## 78. How do you use it to first inventory a messy folder then archive, instead of moving it all at once?

Split inventory and archive into two independent actions. The first step only lets it inventory, such as list all files in this folder, grouped by type; this step is read-only, the result is a list, you can see clearly what is inside. The second step lets it archive, with a confirmation gate, such as move PDFs to the archive directory, spreadsheets to the spreadsheet directory, leave the rest, and list the to-move items for my confirmation before executing. The biggest risk of a messy folder is mixed content and irregular naming; moving all at once easily takes things that should not move. The docs repeatedly stress backing up important files before processing, and checking the target directory and recycle bin first after executing. Inventory first, confirm, then archive; only then can a mess become tidy without losing things.

## 79. Which three scenarios of away from the computer but the thing must be done now is the Remote Assistant best at rescuing?

The first is needing something temporarily during a meeting. You are in a meeting with only your phone, but immediately need a meeting note or supplement; send a sentence on the phone, and the computer-side assistant starts working, the result returns to your phone when done. The second is processing files when out: someone urges you for a desktop material, the Remote Assistant lets you directly have the computer read, organize, and send. The third is arranging ahead during commute: on the road you think of a to-do, throw it over to prepare materials in advance, and continue directly at the office. The docs sum the Remote Assistant scenarios into these: out, in meeting, on commute, temporary need. Its value is loosening the thing that you must sit at the computer to push work. The premise is the computer stays on and running the client, with normal network.

## 80. Why is a task like auto-weekly-report-on-Friday most worth automating first?

Because it meets three conditions at once: periodic, clear rules, no real-time human intervention needed. Every Friday at that time, what to do is almost the same: consolidate this week's progress, classify by module, count key data, generate a concise weekly report. The docs also clearly place automation in periodic, repetitive tasks; the weekly report is the most typical representative. And the weekly report's deliverable is clear, an openable file, simple to accept. Make it a scheduled task, such as set every Friday at 17:00 to auto-run, and it will consolidate, generate, and save to the specified directory on time. You only return to the result area to glance whether the product is right, no need to grind from scratch weekly. Start automation from this most stable task, run it smoothly, then expand to more complex scenarios; the risk is minimal.

## 81. How do you connect external services like Google Calendar and Drive without getting stuck at the start?

Two steps: first get authorization right, then write the task description specifically. For authorization, enter the Connector entry, select Google Calendar or Google Drive, complete account authorization by the prompts; if this step fails nothing later runs. The common stuck point is authorization not succeeding, or the schedule and files you want to read are not under the authorized account. For the task description, give a clear time range and search boundary; do not just say look at my meetings, say view today's meeting schedule; when materials are many also specify folder, keyword, or meeting name to narrow. The docs suggest this too: grant only needed permissions when authorizing, state the time range clearly, narrow when materials are many. First let it only check today's schedule to verify the chain, then move to complex tasks like organizing materials and generating to-dos.

## 82. Why are tasks where you must rethink the instruction each time most worth distilling into a fixed process or Skills first?

Because each time you rethink an instruction, you consume attention once more, and each time what you write differs, so the result naturally drifts. Such tasks share a trait: you have done them more than a few times, steps are basically fixed, but each time you must organize from scratch how to say it. After making it a Skill, next time just trigger an intent and it follows your solidified process, no need to repeat background, format, output location. The docs also suggest starting from high-frequency actions; the more frequent the repeated operation, the more worth distilling. The premise is this process must run smoothly in manual mode first; encapsulating while the manual process is unstable only fixes the chaos. The order is manual stable first, then distill into Skill.

## 83. For building a local app with zero code, what small problem is most suitable to try first?

Most suitable to try a small tool with single function and clear boundary first, such as a local knowledge management tool. Its need is restrained: support add, search, edit, classify, simple interface, fit personal daily recording. Why pick this? Because core actions are few, you can quickly see whether the generated code runs and runs right, and the result-area preview can directly show the page effect without installing a bunch of environments. The docs suggest this too: first make the minimum viable version, finish core functions first, then gradually add complex capabilities. Newcomers most fear wanting a feature-rich app at once, then every step debugging errors, unable to finish a complete loop. Once the small tool runs, try more complex functions like fuzzy search and auto-push; each step has the last stable version as backup.

## 84. In which tasks does AI self-drive mode most easily help, and in which does it most easily lose control?

It helps in tasks with clear goals, breakable steps, and self-checkable middle. Such as collect this week's developments in a field, organize into a brief, attach source links, self-check for duplicate info before output. You state goal, constraints, output format, completion standard once, and it plans the order itself, first collect, then filter, then organize, no need to watch each step. It loses control mostly in tasks with vague goals, no boundary given, and involving high-risk actions. Such as only say help me organize these materials, without saying into what, where to put, whether deletable; it fills understanding itself, and in self-drive mode it dares to act more, easily deleting, editing, overwriting more. The docs remind well: the clearer the goal, the better self-drive works; for complex tasks give boundary first; for deletion, overwrite, migration, preview the plan first then execute.

## 85. In what scenarios does it truly save time, and in what scenarios does it just swap hand-busy for eye-busy and mind-busy?

Scenarios that truly save time share traits: clear task boundary, you have done similar things, the deliverable is directly acceptable. Such as fixed-format data to weekly report, a batch of files renamed by rule, meeting notes to to-do list. It finishes and you open to see if it works; what is saved is real mechanical operation time. Scenarios that become eye-busy and mind-busy are usually you give it a task with vague goal and soft judgment standard, yet cannot help watching each step and correcting it repeatedly; looking busy, most energy goes to correcting and re-explaining, possibly more tired than manual. The criterion is simple: can you yourself state what done looks like. If yes, handing it likely saves time; if no, define it clearly first, do not rush to hand.

## 86. How do you tell which process in your business most deserves to be the next WorkBuddy loop?

Filter by four dimensions. One, frequency: does this process recur, weekly even daily. Two, stability: are input and output relatively fixed, steps about the same each time. Three, deliverable: does it produce a directly acceptable result. Four, risk: are there irreversible high-consequence actions inside, such as outward send, overwrite original. Meeting the first three and with the fourth risk controllable is the most worth prioritizing into a loop. The automation suitability judgment the docs recommend is also this logic: high repeatability, clear rules, no real-time human intervention needed. After picking, first run manually once to verify stable results, then consider distilling into a Skill or making it scheduled automation. Get one loop stable before picking the next; cheaper than spreading several half-finished processes at once.
