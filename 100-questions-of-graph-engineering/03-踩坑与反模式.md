# 第三章 · 踩坑与反模式

多 Agent 出了事，锅很少落在模型质量上。生产复盘里反复出现的是另一类失败：架构看起来优雅，运行起来互相拖累，错误在节点间漂洗，最后连哪里坏的说不清。这一章把那些高频翻车模式摊开，每一条都对应一个具体机制，而不是一句"要注意"。看懂这些，你才分得清哪些图是必须上，哪些图只是把单 Agent 的麻烦换了个更贵的容器。

## 36 为什么搭了 40 个 Agent 的图，反而比一个 loop 还难调？

节点越多，单点故障面越大，这是乘法关系不是加法。单个 Agent 每一步 95% 可靠，十步串起来成功率就掉到六成左右；把五个 Agent 各自跑十步串起来，系统级失败率会高到任何运维都不敢看。四十个节点的图把这种连乘放大到离谱，同时放大的还有协调开销和死锁概率。

显式控制流胜过涌现协调，十次里有九次都成立。四十个 Agent 基本画不出谁跟谁说话的图，画不出就别上线。真正能调试的多 Agent 系统，要么是一个主管带几个专家，要么是固定步骤的流水线，拓扑一眼能看穿。

先问能不能用一个 Agent 加更好的工具解决，再谈加节点。最可靠的多 Agent 系统，往往是 Agent 最少的那一个。

## 37 过度编排是什么，怎么判断我是不是为了图而图？

过度编排指图的结构复杂度超过了问题本身的复杂度，团队是被"图听起来高级"驱动，而不是被真实的数据流依赖驱动。一个常见信号是先挑了框架再想问题，拓扑是为了 demo 好看而长出来的，节点数增加常常只是为了满足对架构完整感的追求，并非任务本身需要。

实用的判据来自一个问题：这项工作到底需不需要显式的状态追踪和条件分支，还是用一个有边界、可重试的工作单元就能成。如果一张图从头到尾没有一条条件边、没有一个环，状态也不超出单次运行的生命周期，那它就是一个普通函数，加图只是多了检查点、序列化和一层抽象，没有任何收益。

图的合法存在需要这三个条件里至少一个：步骤会按中间结果分叉、流程需要回头重做、状态要跨运行保留。判断自己有没有过度，就问一句：把这张图拍平成一个顺序函数，功能会不会丢？不会丢，就先别上图。另一个信号是图的复杂度在跟着团队的组织扩张而不是跟着任务扩张，这时候要先停，回去想清楚数据流到底长什么样。

## 38 子 Agent 之间传上下文丢信息，这个坑为什么这么常见？

上下文传递靠序列化和截断完成。每个 Agent 有独立的上下文窗口，handoff 时只能传压缩后的状态，真正关键的信息常常在压缩时被丢掉，下游 Agent 拿到的是上游的摘要，不是上游的完整推理，它无从知道哪些信息在摘要时被丢掉了。

更隐蔽的是，丢失不会报错。下游基于残缺上下文给出看起来合理的输出，链路照常往下走，错误要到很后面才暴露。生产复盘里那种"前面 Agent 幻觉了一个事实，后面 Agent 把它当真值，再后面把它和真实数据混在一起"的污染，根源往往就是这一次手递手的上下文损耗。

缓解办法是在 handoff 之间放语义校验点，让接收方在并入自己的推理前，把关键断言对照可信来源核一遍，而不是默认上游一定对。

## 39 隐藏循环怎么让 Agent 看着在忙其实啥也没推进？

循环不一定报错，它可能只是不停。最典型的是"礼貌性分歧"：质检 Agent 驳回，生产 Agent 改，质检用另一个理由再驳回，来回几轮每个 Agent 都按自己的指令正确执行，系统整体却卡死。还有那种没有出口的递归分解，子任务越拆越多，永不到达能直接执行的粒度。

这里有个硬规则：你不能问一个 Agent 它是否在循环里，只能用数学证明。具体做法是给每个循环装计数器和上限，或者在编排层检测重复状态，同一状态连续出现三次就判定为循环并升级处理。没有这个机制，循环会一直吃到预算耗尽才停。经验上，每个 Agent 的迭代步数要有硬上限，比如十五步，超了就触发逃逸序列而不是继续转。

看着在忙和真的在前进，是两件事，循环检测是唯一能把它们分开的手段。

## 40 假成功是什么，最终结果很漂亮过程却已经烂了？

假成功指最终输出通过了验收，但中间环节早已出错，只是被后续的润色和汇总盖住了。只评最终答案最容易放过这类系统，因为错误在中间几跳被 polished 成看起来权威的内容，端到端评分反而很高。

机制上有两处。一是评测绑错了对象：只测技术正确性，没绑业务结果，系统把错误但流畅的输出当成了合格，而大多数试点评测量的是单个 Agent 的准确率，不是管线级的成功率。二是自验不可靠：同一个节点先生成再按自己的标准检查，生产者对自己的产出天然宽容。研究量化过这一现象，模型认出自己写的内容、给一批答案打分时给自己写的打更高分的概率明显偏高（例如一项研究测到 GPT-4 认出自己文字约七成三，给自己答案打分偏高约一成；另一项研究里 Claude 偏高约两成半）。

判别假成功要把评测绑到真实 trace 上，看每一步的中间产物，而不是只看最后一个答案。生产里还要做在线抽样，让人或裁判模型定期翻看实际输出。离线测集抓回归，在线抽样抓漂移和涌现的失败模式，两个面缺一个，假成功就会一直装下去。

## 41 重试风暴怎么来的，一个 flaky API 怎么烧光预算？

重试逻辑往往散在多个互相独立的层。HTTP 客户端重试网络错误，工具包装层重试失败的工具调用，Agent 循环层又重试失败的步骤。三层各重试三次，一次上游故障就能在下游放大成二十七次调用。一个网络超时，变成对支付服务二十七次请求。

多 Agent 系统比传统分布式系统更难防，因为传统系统有集中式重试策略，多 Agent 系统常常没有。支付 Agent 失败触发重试，库存 Agent 看到支付状态不确定也重试自己的分配检查，通知 Agent 发现状态不一致又触发自己的重试，几秒内重试量乘十，下游服务被压垮。

应对要 agent 感知的熔断器，它得有"降级"这个中间态，能识别语义失败，比如 Agent 返回 200 但输出是幻觉。重复检测也不可少：同一工具同一参数命中超过三次就断开电路，保留状态供调试并告警。优雅降级比无脑重试重要得多。

## 42 token 爆炸一般从哪一步开始失控？

失控几乎都从同一个地方开始：没有硬上限的递归或工具链。递归分解不干净就产生调用级联，在有人注意到之前已经烧掉几千美元的 token。无界工具链更直白：让 Agent 自己决定调工具直到"做完"，实际会变成两百次 LLM 调用、四十美元，Agent 在第几十轮迷失并陷入循环。

并行分支乘以迭代次数是另一条放血通道。一个 Agent 十次调用，五个 Agent 轻松变成一百次。从单 Agent 切到五个 Agent，同样的工作负载 token 成本涨到三倍是常见情况，还不包括协调开销吃掉的专业化收益。

唯一的防线是硬预算，不可妥协：每任务最大花费、每 Agent 最大轮次、全任务最大总轮次、工具调用预算。没有这些，一个 bug 就能过夜生成一张上万美元的账单；有了这些，同样的 bug 会像遇到限流一样被拦下。

## 43 为什么说按组织架构画 Agent 基本都会翻车？

组织架构是静态的汇报关系，不是数据流依赖。按部门画 Agent，等于让财务 Agent、风控 Agent、运营 Agent 按公司座位排布去协作，它们该不该说话由职位决定，不由数据决定。拓扑应当由数据依赖决定：两个节点之间没有数据依赖就并行，下一个要读上一个的结果才串行。

"五个不同角色的 Agent 自己想办法"在实践中会一直空转、互相推活、产出垃圾，或者悄悄塌缩成一个 Agent 干所有事。显式控制流十次里有九次胜过涌现协调。一条经验准则：如果一张图你画不出谁跟谁说话，就别 ship 它。

按组织架构画图的人，往往还没搞清楚任务的数据流长什么样，就先分配了角色。角色分配是结果，不是起点。

## 44 为什么说图会循环自欺、互相确认就当真了？没有现实锚点的图，又怎么高效放大错误？

多个 Agent 互不质疑，容易把彼此的输出当成真值。一个 Agent 的结论被另一个引用，再被第三个汇总，错误在"共识"里被固化，因为每个环节看起来都经过了检查。没有现实锚点的图，内部每一道检查都能通过，整张图却可能早已漂离现实，变成一个自洽的回声室。

放大错误的机制很具体：上游 Agent 幻觉出一个事实，下游 Agent 把它当真值消费，再和真实数据混在一起传给更下游，到产出时这个幻觉已经和合法信息无法区分。一次手递手的污染，经过几跳就洗白了。

锚点是图内部优化机器无权改写的外部固定节点，比如真实到账的收入、实际执行过的测试、真正留下来的客户、对得上的实物计数。它们把值传进图，但不受图的动态影响。没有锚点，拓扑再精巧也只是把废话组织得更体面。

## 45 上帝 Agent 为什么是反模式，塞 50 个工具会怎样？

上帝 Agent 是一个节点承担规划、执行、验证和所有工具调用，把所有职责塞进同一个提示。它违反的是"一个节点一个操作"这条底线。节点一旦身兼数职，失败时就分不清是哪一部分崩了；从检查点恢复时，几个操作会一起重跑，包括已经成功那几个。

工具塞太多带来三个具体后果。一是工具选择开始出错且常常静默，编排器选错工具或传错参数却不被发现。二是单节点成为整个系统的单点故障，它一挂全停。三是自验再次失效，因为同一个节点既生产又检查，检查形同虚设。

拆分的依据很直白：把规划、执行、裁决分到不同节点。裁决节点用不同的模型、不同的提示，只读结果不读生产者的推理，这种分离是结构性的，比在提示里写"请客观检查自己"可靠得多。

## 46 静默失败怎么让 Agent 吞了异常还假装没事？

静默失败指异常被吞掉，Agent 返回一个空值或部分结果，上游毫无察觉地继续。比如一个专家节点失败，主管当作"这一项没有结果"处理，汇总出来的答案看起来完整，其实缺了一块。生产里那种"三个专家成功、两个失败，系统默默返回了残缺结果却像完整答案"的案例，就是这么来的。

根因常常是异常被吃掉了，或者缺失数据被当成了合法空值。缺失不等于出错，但两者在下游表现一样，就会污染后续所有步骤。

正确的做法反过来：让主管对部分失败有明确策略，而不是默默把残缺结果当完整答案返回。具体说，主管要从标记里读出哪个分支掉了、掉的是什么，决定重试还是升级到人。失败应当是显式的、范围受限的，而不是悄悄把整条流水线带偏。

## 47 上下文投毒指什么，上游给了脏数据下游怎么中招？

上下文投毒指上游产生的错误内容或对抗内容进入共享上下文，下游把它当作可信事实消费。在 Agent 链里它逐跳漂洗：研究 Agent 建立了一个错误事实，写作 Agent 把它当依据展开，编辑 Agent 把它润色成看起来权威的结论，到终端时错误已经和合法信息混在一起，无法区分。

它比单 Agent 出错更危险，因为每个下游 Agent 可能都在自己的准确率阈值内正常运作，污染却顺着链路扩散到每一个消费者。一次源头幻觉，能 cascade 成基于虚构信息的业务决策。

检测架构要在 handoff 之间放语义校验检查点。接收方不信任上游一定对，而是把关键断言对照可信来源核一遍再并入自己的推理。把"上游输出默认可信"这个假设拆掉，是防投毒的第一道闸。

## 48 为什么多 Agent 在线性写作链路里常不如单 Agent 可控省心，只在需要多视角校验时才加分？

线性写作链路没有真正的并行收益，却有完整的污染和成本代价。同一条任务上，单 Agent 能拿到 99.5% 的成功率，等效的多 Agent 实现掉到 97%，差距随链路复杂度拉大。管线一旦中间某步出错，后面每一步都继承它，研究者幻觉一个来源，写作者放大它，编辑把它抛光成错误信息。

多 Agent 在线性链路里引入的额外失败模式，收益却不明显，因为链路本就可以在同一步内由单 Agent 串行完成，可控性反倒更好。多视角校验是另一回事：让多个 Agent 独立分析同一问题，再由裁判裁定冲突，这种 debate 模式把成本推到单模型的 2.5 倍以上，但在法律分类、金融核验、医疗诊断这种错一次代价极高的任务里，错误率的下降值回票价。

所以判断很简单：任务是线性分解、要的是可控和便宜，单 Agent 优先；任务要的是交叉验证、错不起，才上多 Agent。

## 49 我怎么判断现在该加 Agent 还是先修单 Agent 的 prompt？

先问三个问题。单 Agent 失败是因为上下文或工具不够，还是因为它真的需要另一个独立推理体？任务能不能串行分解，分解后每一步是否真的互不依赖？可靠性预算是否容得下复合错误的乘法。

三个问题里只要有一个答不上来，就先别加 Agent。多数情况下，先改提示、加工具、加评测集，比加一个 Agent 更有效。一个带更好工具的单个 Agent，在可靠性、成本、上线速度上经常胜过仓促拼起来的多 Agent 系统。

还有一条更硬的判据：如果一张图你画不出谁跟谁说话，就别上线。能画出的多 Agent 系统，通常是一个主管带几个专家，或者固定步骤的流水线。加 Agent 应该是证明了瓶颈确实在多 Agent 才做的动作，而不是架构审美偏好。最强大的多 Agent 优化，往往是把 Agent 数量减到一个。

## 50 把图当银弹，最常见的代价是哪三种？

第一种，复杂度与调试成本超过问题本身。图的抽象层、检查点、序列化在简单任务上全是净负债，问题用一个函数就能解决，却背上了整套编排心智负担。

第二种，协调开销吃掉专业化的收益。多 Agent 理论上靠分工变强，但协调、handoff、冲突解决吃掉的时间和质量，常常让整体不如一个调好的单 Agent。同等工作负载下，从单 Agent 切到五 Agent，token 成本涨到三倍是常见账。

第三种，银弹心态本身。最可靠的系统往往 Agent 最少，可银弹心态让人忽略这个事实，把"上图"当成进步本身，在不需要图的地方硬上图。同等工作负载下从单 Agent 切到五 Agent，token 成本涨到三倍，协调开销还会吃掉分工带来的收益，代价全由后续维护者付。

## 51 为什么有些团队花几个月建多 Agent，改改 prompt 就够？

他们把顺序搞反了。先画了一张多 Agent 架构图，再把问题往里塞，而不是先验证单 Agent 是不是真的到了天花板。结果大把精力花在搭分布式协作、处理死锁和状态共享，而这些麻烦单 Agent 加好工具根本不会有。

正确顺序是反过来的：先用单 Agent 加成熟工具跑起来，配好评测，确认瓶颈确实出在"需要多个独立推理体并行或交叉验证"，再加 Agent。带好工具的单 Agent，在可靠性、成本、上线速度上经常胜过仓促拼起来的多 Agent 系统。

那些"改改 prompt 就够"的案例，症结几乎都是过早分布式。把本该在单 Agent 层解决的提示、工具、评测问题，错误地上升成了架构问题，代价最后都落在故障率和单位经济上。

## 52 重复扣款、重复发消息这类副作用，图里怎么防止？

图会重跑，重跑就会重触发副作用。崩溃后从检查点恢复，如果恢复的是消息历史而不是带去重标记的状态，节点重放就可能重复发邮件、重复扣款。

防法是把副作用做成幂等。每个外部动作带一个幂等键，比如任务标识加动作类型，同样的键重试不重复执行。把发消息、扣款这类动作限制在受控节点里，不让图随便重跑就出错。检查点恢复时配合幂等键，恢复的是状态对象而非裸消息历史，这样重跑不会二次触发。

底层逻辑是：副作用必须落在图的受控边界内，图外只放纯查询和无害操作。一旦出错就对外界有后果的动作，绝不能放在可能被反复执行的路径上而没有去重保护。幂等键通常由任务标识加动作类型组成，重试时系统先查这个键是否已执行，已执行就跳过，从根上断掉重复扣款和重复通知。

## 53 框架绑太死，换一个就全废，这个坑怎么提前避？

拓扑设计应当框架无关。先把状态机和边界画清楚，框架只当执行引擎，这样换一家不至于推倒重来。问题出在把框架专属语义写进了业务逻辑：reducer 怎么合并、interrupt 怎么挂起、检查点怎么存，这些如果和业务规则混在一起，迁移时全废。

工程偏好重的团队越来越倾向于纯代码方式定义 Agent 图，要的就是对图结构的完全控制，不想被框架抽象挡在中间。开源栈加可移植的运行时，比绑死在单一专有 runner 上更抗风险。

具体做法是把编排逻辑和运行时解耦，业务规则用框架中立的方式表达，框架专属机制只出现在薄薄的适配层。这样哪天框架不合适，换执行引擎的成本是重写适配层，不是重写整张图。拓扑先按数据依赖画状态机，框架只决定节点怎么被调度、状态怎么被持久化，这层替换不该牵动业务规则本身。

## 54 营销号说的 85% 降本为什么不能直接信，要看什么？

85% 这类数字多来自厂商或分析机构的报告，不是中立结论，且往往带着范围限定被摘出来当口号。行业里有更诚实的观察：运营多 Agent 系统的成本确实在降，但降得没营销说的那么快，而且在不同用例上极不均匀。

同等工作负载从单 Agent 切到五 Agent，token 成本涨到三倍倒是常见的真实账。要看的首先是基准口径：是不是同一个任务、同一个工作量、同一个质量线下比的？很多降本宣传漏掉了运维人力这个大头，也漏掉了为可靠性补上的观测和熔断基础设施。

其次是单位经济而不是百分比口号，同样花的钱换来了什么质量、什么延迟、什么故障率。判断标准很朴素：凡是只给一个亮眼百分比、不给对比条件和口径的，都先当营销看。真值在你自己的任务上跑出来的数字，不在别人的发布会里。

## 55 工具返回的内容劫持 Agent（tool-output prompt injection）怎么把图变成 RCE 入口？

工具返回的内容，比如抓回来的网页、读到的文件、调到的 API 响应，里面可能藏着对抗指令。Agent 如果把这段内容当指令执行，就会越权去干它本不该干的事，图的边界在这一刻形同虚设，正是标题里说的把图变成 RCE 入口的那道缝。

间接注入经几个面进来。工具返回的网页、文件、API 响应本身就是对抗内容的载体；记忆库和 RAG 存的历史文档，如果来源不可信，里面藏的注入会在检索时被带进上下文。间接提示注入的狡猾之处在于，恶意内容从不出现在你给的初始提示里，而是藏在 Agent 自己去拿的数据里。

防护有几道：工具输出用结构化 schema 约束，避免自由格式里夹带指令；输出做消毒；把工具输出当数据而非指令处理；跨节点的授权做到 fail-closed，授权上下文不清就拒绝对外动作。这几道合起来，才把"图"从被劫持的入口变回受控的执行结构。
