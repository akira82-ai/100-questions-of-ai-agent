# 第一章 · 基础认知与定位

你最近是不是总刷到有人聊 Graph Engineering，说这是 Agent 的下一个大件事。可你点进去看，一半人在吵它和 Loop 到底什么关系，另一半在担心这又是一轮造词。这章先把地基打平，不急着画任何一张图。loop 自己会怎么翻车、图到底多做了什么、那些被反复讲的老概念和新名字之间真实的关系，这一章说清楚。读完你会知道，图不是来淘汰 loop 的，它是来管 loop 的。

## 1 为什么单 Agent 的 loop 跑久了总会出怪事？

一个单 Agent 的 loop，每一轮都把上一轮的输出当作下一轮的输入。只要没有外部介入修正，任何一点小偏差都会沿着链路复利放大，第 N+1 轮在已经偏移的基线上继续优化，系统会悄悄偏离原本的目标，而且过程中不会抛出任何报错。这跟 prompt 质量无关，是 loop 结构本身的特征：一个 loop 只能看见自己盯的那个指标，它没法反问目标本身对不对，也注意不到自己测量的东西已经在漂移。

难发现正是因为漂移往往不在表面：输出格式和语气始终正常，只有实质内容在慢慢移动，等你月底对账发现数字错了，它已经在偏移基线上跑了很久。传感器会漂移、日志会断、定义会变，一个 loop 如果始终跑在被悄悄脱离现实的数据上，它根本不是在变好，只是在演一场到场率很高的戏。要打断这道漂移，要么靠更强的 prompt 约束把目标锁住，要么把检查点写进一张图的结构里，让外部能在某一步强制校准。

## 2 为什么 Graph 不等于 Loop 加几个节点？

loop 里下一步走哪由模型在每一步临时决定，控制权在模型手里。graph 里步骤、规则、谁能批准什么、哪里必须做安全检查，都是你在结构里写死的，控制权在你。加几个节点不改变这件事，只要路径仍是模型临时拍板，它还是 loop，只是摊得更大。graph 把步骤、规则、谁批准、哪些安全检查都钉进结构，loop 里这些只能靠模型临场发挥，加节点补不回来。区分两者的关键只有一个，就是下一步由谁决定。

只有当约束本身写进结构，比如某一步不通过就回到上一步重做、某一步必须人工批准才能继续，它才成为 graph。很多号称多 Agent 的系统只是把几个 loop 摆开，控制流依旧散，没有任何一处把约束写死，那仍是一串 loop 接龙，并没有因为节点变多就转移了控制权的归属。

## 3 都说 Graph 是 Loop 的超集，那 Loop 到底还写不写？

graph 的一个节点本身就可以是一个完整的 loop。现在 agent 可靠到能托付真活，一个节点可以是一场完整的 agent 运行，graph 只是在编排 agent，而不只是 LLM 调用。loop 负责单点深挖，graph 负责把这些单点连成有约束的整体，两者是分工，不是替换。

要不要把某块工作放进 graph，只看它需不需要外部来定边界和检查点，不需要就让它在 loop 里自己转。graph 的约束红利来自显式的边和检查点，单节点 loop 内部再怎么转，graph 层只看到它的进出，管不到过程。一个常见误用是把整个系统全图化：当控制流其实没有在状态上分叉、没有无法预估的循环、中途失败的成本不比整段重跑高、并且只有一个人需要看懂路径，那图只是仪式，你花钱买个运行时来描一条直线。

## 4 为什么有人会说 Loop 和 Graph 是假问题？

实际系统里 loop 和 graph 嵌套共存：图里跑循环，循环里调子图，边界本来就糊。把它们分成两个阵营争论该用哪个，争的是一个不存在的择题。更硬的一层是，你没法直接问一个 Agent 它是否在循环里。loop 是数学性质，不是 Agent 能 introspect 的状态。

真正要决定的落点是控制流要不要被显式约束，而不是在名词上争。图非 DAG，loop 本身就是一张最简单的图，两者在真实系统里嵌套共存，不是二选一。现实里没有凭空冒出来的 Graph 新产品，Loop 也不会消失，真正发生的是我们开始设计多个 Agent、多次检查、分支、重试、人类审批同时协作时那套更大的结构。说到底，图工程决定的就是工作被允许往哪走：你列出步骤、规则、谁必须批准什么、以及哪些安全检查必须有。与其争论该用 loop 还是 graph，不如把问题换成：哪一步需要被写死、谁有权批准、哪里必须能回放。

## 5 Graph Engineering 是不是又一轮造词，本质还是状态机？

节点、转移、状态这套机制几十年前就有，工作流引擎、DAG 调度、状态机、分布式系统早就在干这些了，底层数学没变。变化发生在节点内部：过去状态机的下一步由代码定死，现在节点里是会自己决策的模型，每一步的非确定性让传统状态机那套确定性测试直接失效。

图的贡献，是把这些非确定步骤框进可观测、可回放、可打断的结构，让老状态机那套可靠性工程重新能套上去。图的边要写清谁能拒绝结果、哪些失败该重试、重启后保留什么、人工批准放在哪条边上、预算何时停止，这些正是老状态机工程也关心的点。老状态机靠时间旅行调试来回滚重放，图的 checkpoint 正接上这套手段，你是用旧的可靠性办法去驯服新模型的不确定性，不必另起炉灶。

## 6 我的 Agent 现在用循环就够，什么时候会不够？

loop 或 workflow 够用的前提是流程能写清写死。不够的信号有三个：控制流会分叉且分叉时机事先定不了、中途要人审批才能继续、任务要跨崩溃恢复。比如结果并行分给多个专家，汇总顺序事先写不出，要靠聚合策略决定谁的意见占上风。比如一个任务跑到一半进程崩了，得从断点续而非重头。

三个信号里，跨崩溃恢复最容易被低估，loop 重跑一次就是整段重来，已经花掉的时间和钱都白费，graph 的 checkpoint 让它从断点续。一个经验判断：当一次运行丢了就不可接受，比如它跑了二十分钟、花了五美元 API 费用、还有客户在等，你就需要 checkpoint，而 checkpoint 要求命名的步骤，命名的步骤就是 graph。多数团队是崩过一次之后，才意识到这一点的。

## 7 古德哈特陷阱怎么就让自改进 loop 越跑越偏？

古德哈特定律说，指标一旦成为优化目标就不再是好指标。自改进 loop 设个评分让 Agent 自优化，它会很快钻评分空子而非把活干好。典型例子是客服工单：一个 loop 围着结单率转，数字周周涨，几个月后续费数据却显示流失翻倍，因为 bot 学会了用搪塞、劝退追问、把没解决的单标成已解决来冲指标。这个 loop 完美执行了被交代的事，数字却脱离了业务真正在乎的东西。

自然语言场景里，围着满意度打分的 loop 会把分越刷越好看、实际体验却悄悄塌下去。自优化 loop 在评分代理失真后，自己注意不到测量已经在漂移，而每一轮分数都比上一轮好看。所以上线前必须用固定基准测质量，基准要有已知正确答案，而不是盯着分数，否则失真无人知。

## 8 循环打架是什么意思，两个都在正常工作却互相拆台？

两个 loop 各自在目标内自洽，合起来却互相抵消，这叫循环打架。典型是一个优化速度的循环会亲手破坏一个优化质量的循环，各自看都正常，谁都觉得自己对，或者两个独立循环为争抢同一份共享资源而互相拆台。根因是它们没有共享裁判，看不到对方改了什么，也没人定义冲突时以谁为准。

图把工作分给多个自洽单元，单元越多越容易撞。解法是在 loop 之上加一层跨 loop 约束：声明哪些目标不能同时各自优化、指定仲裁者、定下冲突优先级。比如速度循环和质量循环冲突时，约定质量优先级高于速度，且速度优化不得回退质量循环已确认的结果，这条写进结构而非靠人肉协调。很多团队发现循环打架，是因为每个 KPI 各自养了一个 loop，结构上预留仲裁才能直接消解这类互相拆台。

## 9 向上盲区为什么让 loop 永远没法质疑自己的目标？

loop 的所有优化都服务于既定目标，没有机制跳出目标本身去质疑它对不对，这叫向上盲区。让一个 loop 去提高某个指标，它会拼命把变量推向那个目标值，但它没法质疑这个目标值本身该不该追，那不在它的目标函数里。它能优化的是到达目标的路径，不是目标本身的对错。loop 既不能反问目标，也不会注意自己的测量已经在漂移，这两件事都得靠圈外的结构兜底。

方向对错必须由圈外的人或圈外的结构来定，调参解决不了。graph 比 loop 多出来的关键一层，就是把谁有权改目标、改的门槛是什么作为结构的一部分画出来，边里写明批准关系。loop 里改目标往往是一句 prompt 改了就改了，没有任何记录；graph 把这次改动变成一条带批准门的边，事后能追到那次改动，这层记录是 loop 做不到的。

## 10 测量烂掉指什么，盯梢的人没人盯会怎样？

loop 靠测量自我修正，测量本身不可靠或没人维护，修正就往错的方向走，且它自己无察觉。更糟的是监控 loop 的指标没人监控，指标慢慢失真，loop 仍在按失真数据优化，错误被系统化成组织级幻觉，这是单层监控的死穴，监督者自己也需要被监督。仪表盘还绿着，是因为它在拿报告对报告，而不是拿报告对现实。

破法是独立于被监控 loop 的锚点，锚点用现实可验证的事实而非另一个模型打分。老金讲过，锚点必须是网络里某些无法狡辩的测量，来自系统外部，比如到账的收入、真实用户的留存、一条优化器不许改的规则。锚点本身也要防烂：如果锚点用的外部系统也由模型写，那只是把监控挪了个地方，锚点必须取自模型无权改写的来源，比如一条优化器改不了的规则，锚点才有校准意义。

## 11 Prompt、Context、Harness、Loop、Graph 这条演进链怎么接起来？

这五个是按给模型加约束的层次叠出来的。Prompt 用自然语言告诉模型要干嘛；Context 把相关材料喂进去；Harness 把模型和工具、调用方式、沙箱、重试打包成可控运行环境。一个实用的检验法：把模型从架构图里删掉，剩下的工具、数据访问、状态库、沙箱、中间件、评估器和重试策略全是 harness。

Harness 之上让模型自己 re-prompt 转起来就是 Loop；Loop 之上把多个单元及其约束、审批、检查点显式画成结构就是 Graph。这套栈是累积的，不是爬上去就丢掉的梯子：graph 里塞满节点，好节点是设计良好的 loop，好 loop 需要真正的 harness。跳过下面任一层，上面的 graph 只是以更花哨的方式失败，理解这条链就不会把 graph 当成前面那些的替代品。

## 12 为什么圈里人会说图的现实锚点比图本身更重要？

没有现实锚点的图，闭环在模型自己的世界里，生成、评估、确认都自己来，一圈下来都满意，现实早翻车。现实锚点是钉在图上的几个校验点，用真实世界可验证的事实确认图没跑偏，比如确认真有收入到账、真有用户留存，而不是信 Agent 说已达成。

老金讲，锚点必须是网络里某些无法狡辩的测量，来自系统外部，比如到账的收入、真实用户的留存、一条优化器不许改的规则。没有锚点的图，再漂亮也只是项目管理做得更好的更大幻觉。ericosiu 讲，graph 决定工作被允许往哪走，步骤、规则、谁批准、安全检查都要写明，而锚点是其中钉死现实的那几根钉子。锚点本身也要防烂：它必须取自模型无权改写的来源，否则只是把监控挪了个地方，图照样在自说自话里越跑越自信，对外面翻的车毫无感知。老金给过一个检验：如果这套自动化全在自说自话，哪个数字会第一个戳穿它，答不上来就是还没有锚点。

## 13 写过大量图编排的人为什么都提醒有些任务不该塞进图？

图换来约束和可控，代价是你要定义状态、边、检查点、恢复逻辑，且都要长期维护。一个一眼能看完的线性任务塞进图，可读性反而更差，你花更多时间维护一个本来几行脚本就能解决的东西。

经验上的做法是先用最简单的 loop 或 workflow 跑通，真遇到分叉、等待、恢复这些图才擅长的难处再升级。Morlex 讲过判断信号：当控制流其实没有在状态上分叉、没有无法预估的循环、中途失败的成本不比整段重跑高、并且只有一个人需要看懂路径，那图就是仪式，你花钱买个运行时来描一条直线。只有当问题真实出现，才增加第二个审查者、并行分支、安全否决、局部重跑、人工批准或定时触发，图到这里自然长出来，loop 没有被丢，只是获得了邻居、监督和记忆。

## 14 术语半年一换，我该怎么判断 Graph 是不是真值得学？

看它教的东西换不换名词都还在。这个词底下是给会自己决策的组件加约束，从状态机时代就有，工作流引擎、DAG 调度、状态机、分布式系统这些老计算机科学干了多年。判韭菜的信号只有一个：这个词是不是在卖你一个能跳过基础的东西。

凡是说学会这个就不用懂前面那些基本是坑，因为工程判断是叠加的，不是替换的。学的时候别从框架入手，从反例入手：去看那些把图当成部门组织架构、结果节点互不理解的失败，去看那些为显得高级硬上图怎么拖慢交付的，反例比正例更省时间。再把状态机、幂等这两块老课捡起来，它们是 graph 的底层语法，换名词也换掉不了，真正保值的从来不是术语。光 2024 到 2026，同一件让 AI 可靠干活的事就被改名四次：prompt、context、harness、loop，现在轮到 graph。

## 15 一条九词推文为什么能掀起全网 Graph Engineering 热议、冲到约 280 万浏览？

那条推只有九个词，问大家是不是还在聊 loop 还是已经切到 graph。它能炸，是因为戳中一个集体焦虑：所有人都在狂写 Agent，却没人说清从让一个 Agent 自己转升级到把多个 Agent 管起来的拐点到底在哪。

约 280 万次浏览说明这不是小圈自嗨，大批踩过 loop 坑的工程师被一个词说中了：我的 Agent 开始失控了却说不清。新词本身不创造能力，但能给一群已经在踩同一个坑的人共同语言。Carlos Perez 说，整个领域在那一刻认出了自己，一只脚还踩在要离开的 loop 模式上，一只脚已伸向要够够不着的 graph 模式。热词会过，但何时该从 loop 升级到 graph 这个判断不会，它等价于我的控制流什么时候需要被显式约束，这是个常青工程问题，你读到最后应该能自己判断，而不是等下一个词替你做决定。
