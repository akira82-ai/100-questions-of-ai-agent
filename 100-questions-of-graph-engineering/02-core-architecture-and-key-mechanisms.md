# Chapter 2 · Core Architecture and Key Mechanisms

Most people writing their first graph hesitate between nodes and edges. What goes in a node, where an edge connects, how state flows. Until these three questions are clear, every agent you add is just adding to the chaos. This chapter does not pile on nouns. It takes the graph's skeleton apart: what nodes, edges, and state each govern, why none can be missing, and how those fancy-looking production graphs are still just these few things turning underneath.

## 16. Why are a graph's nodes, edges, and state all indispensable?

A node does the work. A node can be a deterministic piece of code, one model call, one tool call, or an entire sub-agent with its own loop. An edge decides where to go after this step, some hard-coded as a fixed path, some chosen dynamically from the node result or current state. State is the information flowing through the whole graph; every step reads and writes it, and it is also a typed dictionary spanning the graph that every node can read and write, with the runtime responsible for ordering, persisting, and recovering it. Seen separately, each is simple; together they make a runnable graph. Nodes without edges degrade into a pile of isolated functions that never call each other. Edges without nodes have a pretty path but nothing to execute. Without state, every step starts from zero, and retry, resume, and audit have no anchor. A graph fixes what to do, in what order, and with what information, all at once in the structure. Missing any one reverts you to a plain script. Viewed as a state machine, it defines the workflow, the state flowing within it, and the transitions between steps. None of the three can be omitted.

## 17. People say a loop is a simple graph. Where exactly is it simple, and what does it lack?

A single-agent loop is a directed cyclic graph: the node is the think-and-act step, and the edge connects it back to itself. A loop is the minimal form of a graph, not its opponent. It is simple in having only one node and one back edge, with no branch or merge to design, no worrying about who passes to whom. What it lacks is the ability to arrange multiple different work units into a network: by definition a loop is sequential, it can only spin in one context at a time, it cannot fan out sub-tasks in parallel, it cannot let different experts each own a segment, and it cannot insert a human approval in the middle. When you need a structure that specifies who nods at what, when, and for what, a loop cannot give you that skeleton; it can only rely on the model's improvisation. In a graph framework, one node's back edge already forms a loop, and only when it needs parallelism, approval, or per-step model switching is it worth expanding into a multi-node graph. To decide whether to upgrade from loop to graph, see whether the task truly spans multiple units that need separate constraints: independent parallel branches, different models per step, mid-way human approval. Hit any one and graph; otherwise a loop is enough.

## 18. DAG or cyclic graph: which should I use? Must a graph be acyclic?

Not necessarily acyclic. A DAG fits work that runs straight through without looking back: classify, then retrieve, then synthesize, each step only forward. But once a system needs to retry a failed tool call, ask the user for missing information, rework after validation, or pause for human input before continuing, it inevitably carries cycles. Production agents almost all need loops: retry, follow-up, rework, pause for human input then continue. These actions cannot fit in an acyclic structure. Choose DAG or cyclic graph by whether the flow looks back. Pure pipelines use DAG; anything with a "do it again" or "wait for a person" accepts cycles. Forcing a cyclic flow into a DAG only hides the loop inside some node, burying the real circuit in implementation details, invisible on the structure diagram and harder to debug. Acyclic just means topological sort finishes and you are done; it is the cycle that accommodates the core actions of agent systems. First ask whether the flow looks back, then decide whether the graph needs cycles. DAG fits the classify-then-retrieve-then-synthesize line; only a cyclic graph holds the looping actions of agent systems.

## 19. Why are production graphs often not DAGs, while textbooks always teach DAGs?

Compilers and data processing often model tasks as DAGs; once dependencies are topologically ordered, you are done, and acyclicity means no deadlock and easy parallelism. But an agent's next step often comes from runtime judgment, not static dependency. Follow-up questions to the user, retries, rework, waiting for approval, these actions a DAG cannot hold. Production agent graphs are usually not DAGs because the loop is the core action of agent systems. A graph does not have to be a DAG; it accommodates cycles, a state machine that permits circuits: it defines the workflow, the state flowing within, and the transitions between steps, and the circuit is a legal component. Treating the loop as a first-class citizen lets you express the real behavior of agent systems faithfully, otherwise the loop is just stuffed inside some node, invisible on the structure diagram and hard to debug. Textbooks give you a clean mental model; production forces you to accept the cyclic reality. The difference is whether the next step comes from static dependency or runtime judgment.

## 20. How can a deterministic path and an agentic step coexist in the same graph?

In one graph, deterministic steps and model-autonomous steps can sit side by side. The key is who is in charge at which slot. Fixed operations become deterministic nodes; the model steps in only where judgment is needed: classification uses one tool-free model call, synthesis uses one generation, open exploration goes to a sub-agent with its own loop. Model inference appears where it truly adds value; everything else goes to code, making the system cheaper, faster, and more predictable. In a document agent example, fetch requests and linear operations are driven by fixed code and API calls; classification and synthesis use single model calls; two sub-agents for reference docs and concept docs do the open-ended work, the three each playing their role on the same graph. Using different models at different steps is also a common coexistence: retrieval uses a model with search permission, drafting uses a large-context-window model, review uses a cheap fast model. On the same graph, retrieval, drafting, and review can each use a different model. This is the specimen of mixing deterministic and autonomous.

## 21. Why should state be a typed structure instead of being stuffed into the chat log?

Stuffing state into the chat log means each agent guesses from a large block of natural language what the previous step gave it. Field names change, types mismatch, formats drift, and downstream can only reconstruct meaning, with errors hard to locate. Typed state fixes the shape of data passed between steps: which fields, what types, which values are allowed, all written into the structure. Data that violates the structure fails at the boundary instead of quietly polluting downstream, and debugging shifts from guessing meaning in logs to which structural rule this payload broke. Across multiple agents, typed state lets each node read what it needs and write what it produces; state replaces hoping the model remembers what happened a few steps ago. Typed state also requires each field to have a type and a default value, and when multiple nodes write the same field you must define how to merge. Getting the schema wrong means hitting type errors at every node. Once state is explicitly a typed structure, retry, resume, and audit land on specific fields, which is the precondition for a graph to be as reliable as a program.

## 22. How do you write conditional edges without degrading them into a pile of nested if-else?

The difference between a conditional edge and if-else is where the branching logic lands. If-else scatters branch logic through the code; a graph collects "under what condition go which way" into the edge itself. In practice, do not write a pile of judgments inside a node and jump manually. Instead let the edge read the state or node result and return a target node name. A conditional edge is exactly a routing function that checks state and returns the next node name; the branch lives in the edge, not the node. This makes branches visible, testable, and drawable on an observability panel. A fixed edge always leads to the same next node; only a conditional edge runs a routing function that checks state and returns the next node name. Keep them separate so the structure diagram alone explains the direction. The signal of degrading into nested if-else is: to change one branch you must touch the internal code of several nodes, and no one can state the flow just by looking at the structure diagram. Edges carry conditions, nodes only do work; separate the responsibilities and the routing logic no longer scatters in the node's ifs. A conditional edge can pick the next node based on the node result, current state, or external signal; the routing logic henceforth lives in the edge layer.

## 23. When should you use a subgraph to encapsulate an expert's internal flow?

When a sub-agent's internal flow is complex enough to deserve its own block, encapsulate it as a subgraph. The outer graph only cares about handing it the task and getting the result back, not how it spins inside. The supervisor-worker pattern is often implemented as a subgraph: the supervisor decomposes the task and routes to specialized worker sub-agents, whose internal steps are encapsulated, exposing only input and output. The subgraph is internally self-consistent while the outer layer stays flat, with the interface exposing only input and output, so reuse, testing, and recovery points can be added to that block alone. Use it when this flow is reused in many places, its internal steps change often but its external contract is stable, or you want to add testing and recovery points to this block specifically. Do not use it when it is called only once with just one or two internal steps; encapsulating then only adds a layer of indirection. A subgraph is a tool for paying for complexity, not a default action; used wrongly it adds cognitive load. Encapsulated well, the outer graph reads like a one-line function description; encapsulated badly, it adds another layer to guess.

## 24. What does dynamic dispatch solve that an ordinary edge cannot?

An ordinary edge is fixed when you draw the graph: A connects to B, B to C. But some work, the number of downstream nodes, is only known at runtime. The typical case is divide-and-conquer: split the input into pieces, send each to a worker, then aggregate, and the number of pieces depends on the input itself. Dynamic dispatch lets a node decide at runtime how many pieces of work to send to which downstream nodes; the connections are not hard-coded. It solves work with known structure but unknown scale: you know you will fan out then aggregate, but not how big the fan-out is. Without it, you can only give a conservative fixed upper bound, and waste or shortage are both inevitable. Graph frameworks use Send-style primitives to let a node dynamically route work to one or more downstream nodes at runtime, without statically hard-coding each transition. The cost is that you must write the termination and aggregation logic clearly yourself: when is the fan-out done, and should you deduplicate before aggregating. A static graph thinks that through for you; a dynamic one makes you define it. Research tasks often fan out then synthesize, but exactly how many to fan out is unknown upfront, which is exactly dynamic dispatch's use, while static edges can only approximate.

## 25. Why must state be shared across runs? What lets a graph resume after a restart?

When an agent crashes halfway, a restart should not start from scratch. It relies on externalizing state: after each step, write the current state to storage outside the process, and the next step reads from there. A checkpoint is the state snapshot saved after each step; on crash the graph resumes from the most recent checkpoint. Sharing across runs also means multiple instances, or a human returning days later, can all pick up the same state. The cost is designing clearly what to store, how often, and how to skip already-executed side effects on recovery. Leave state in memory and a restart loses it; externalize state and the graph gains for the first time the ability to pause and let a person continue, which is also the precondition for running long tasks, something a loop rarely has naturally. The externalized durability layer itself must be reliable; using a memory cache that loses data as the state store equals no externalization. Production commonly uses Postgres or Redis as the checkpoint backend; an in-memory cache should not be used in production outside tests.

## 26. Is human approval a node or an edge in a graph? How big is the difference?

It can be either, and the difference is semantic. As a node, approval is an explicit procedure: a person reaches this step, looks, approves or rejects, and the flow continues. It occupies a visible position in the structure, observable, accountable, and recognizable by skip logic. As an edge, approval is a constraint that someone must nod before taking this path, lighter, not occupying an independent procedure slot. For steps needing accountability and observability, prefer a node so approval is visible at a glance on the graph. A human gate as an interrupt point lets the graph pause and wait for external input; the state stays in the database, the process can shut down entirely, and after the person responds it continues from the same checkpoint. Lightweight confirmation prompts are fine as edges; anything involving money, external actions, or compliance becomes a node, leaving a traceable footprint. Production more often makes it a node, because you need to say clearly who it is stuck with, how long, and why rejected, which only a node slot can carry. When approval is a node, who it is stuck with, how long, and why rejected can all be read directly from the structure, so accountability and observability hold.

## 27. Who decides which path to take next: the model or me?

In this graph, some routing is hard-coded by you, some is handed to the model. Hard-code deterministic paths so the model does not re-guess every time; let the model choose branching that needs judgment based on state. The principle of division: anything whose rule can be stated in advance is set by code, do not bet on the model being right each time; only what truly depends on context and cannot be hard-coded lets the model decide. Let the model be in charge where it should be, and force deterministic behavior where it must be forced, rather than hoping the model gets it right each time. A routing function checks retry_count over a threshold and diverts to error handling, checks approval_status passed before continuing, or sends the task to the corresponding expert node based on classification result. These are code-set rules, not the model deciding on the fly. All hard-coded loses flexibility; all handed to the model loses control. The balance point is the graph's skeleton. Treating which step the model decides and which is hard-coded as a design variable is why a graph is more predictable than a pure loop: orchestration is not left to the model's improvisation.

## 28. How do you choose among supervisor, hierarchical, swarm, and fan-out-fan-in topologies?

The four common arrangements correspond to different collaboration styles. A supervisor splits the task to experts and collects results, fitting tasks that cleanly decompose into sub-blocks. Hierarchical is the supervisor's generalization, nested multiple layers, fitting large tasks split across layers. A swarm is agents of equal rank reading and writing on a shared blackboard, fitting exploratory work where you do not know how to split upfront, but it easily drifts. Fan-out-fan-in spreads out in parallel first then synthesizes, fitting mutually independent, parallelizable sub-tasks. In production, default to choosing between supervisor and graph: use supervisor when the task decomposes clearly, use graph when the control flow carries conditions and needs observability. Supervisor-worker and graph are the two truly cost-effective multi-agent patterns in production; swarm and blackboard are theoretically interesting but rarely beat the first two. Swarm is only used in exploration or research modes, not in the production main line, because without a supervisor anchor the goal easily loses focus. A supervisor almost always beats a swarm in production because it anchors goal alignment, while a swarm without an anchor drifts. Hierarchical is the supervisor's generalization, fitting large tasks split across layers.

Break the workflow down and the shapes that cover most cases are just a few. Fan-out fires N independent jobs at once instead of queuing, and the key is that one failure returns empty without sinking the batch. Fan-in adds a barrier that waits for all upstreams before proceeding, but that should be the exception, not the default. A diamond connects fan-out and fan-in: spread out in parallel, merge and dedupe in a few lines of plain code, then have one agent synthesize. Routing lets one node pick which edge to take based on the result, with the classifier as a model and the routing itself as plain code. Verification hangs a verifier on an edge whose only job is to try to falsify the result, and only proceeds if it cannot. A converging loop is for work whose size is unknown upfront, with the rule to stop only when round after round digs up nothing new. These map to the dynamic workflows the industry has summarized: act after classifying, synthesize after fan-out, adversarial verification, run until done, plus generate-then-filter and tournament.

## 29. Why does picking the wrong topology often cost more than picking the wrong framework (but don't ignore the long-term cost of framework lock-in)?

Topology defines the collaboration structure; the framework is only the tool that implements it. A system that uses a swarm but needs strong goal alignment will drift for lack of a supervisor anchor, and no framework swap can save it. Conversely, if the framework is wrong, most patterns can be rewritten elsewhere; migration has a cost but is not a structural dead end. Decide topology first, then framework. But framework lock-in is a real long-term cost: once productionized, the graph's state format, durability layer, and observability are all bound to one vendor, and the rewrite cost jumps. Frameworks have converged to support these standard patterns, so the cost of rewriting to switch frameworks is usually not worth it; therefore think through topology first and treat the framework only as an execution engine. Do not sacrifice structural correctness to dodge framework binding, and do not obsess over selection while ignoring lock-in. Multi-agent patterns are supported across mainstream frameworks; choose a framework by team familiarity and ops integration, not by whose unique capability. Patterns are portable across frameworks; switching frameworks usually only requires rewriting the execution engine, not overturning the topology. Wrong topology is a directional problem; wrong framework is an engineering problem. Guard both.

## 30. In principle, what does a graph's recoverability recover: nodes, the whole state, or a layer in between?

In principle it recovers the state object, not the nodes and not the whole graph. A node is a stateless computation unit that produces output given input; recovering it alone is meaningless. Rerunning the whole graph is too expensive, and side effects would repeat. What truly must be stored is the state snapshot after each step: after a crash, read back from the most recent snapshot and replay the steps not yet done. The layer in between is the side-effect boundary: actions already taken on the external world, messages sent, money charged, cannot be compensated by replay and must be skipped via an idempotency key. The sound approach to side-effect isolation is separating decision from execution: a decision node says it should send, an execution node checks whether it has already sent before sending, so the decision node can be safely replayed and the execution node avoids duplication via the idempotency key. The difficulty was never storing the snapshot; it is isolating the actions that cannot be stored back. An idempotency key is the concrete implementation of side-effect isolation; it checks whether the action was already done before executing, guaranteeing a crashed recovery sends the same message only once. Drawing the side-effect boundary clearly makes recovery a clean rerun, not a replay of disaster.

## 31. What is the difference between multiple agents sharing a state object versus passing messages to each other?

Sharing a state object means multiple agents read and write the same structured data, making who changed what clear at a glance, fitting collaboration needing a consistent view, but it needs concurrency control, otherwise two agents writing at once step on each other. Passing messages means each agent sends a chunk of content only to its downstream, looser coupling, more like a pipeline, but the global view is scattered, no one sees the whole, and troubleshooting means stringing the messages together. The difference is shared memory versus messaging: shared state is strongly consistent but conflict-prone; messaging is loosely coupled but hard to trace. A multi-agent system without shared state is like a relay race where each runner does not know where the previous one ran. Complex collaboration often mixes both: shared state holds the truth, messages drive the flow. When you start using message content to reconstruct the current system-wide state, that is the signal to move to shared state. Concurrent writes to the same field need locking or agreed ownership, otherwise later writes overwrite earlier ones and who changed what is hard to trace. Giving each node its own separate tool permissions is one way to avoid shared-resource contention, keeping parallel nodes from grabbing the same external resource.

## 32. Why can a graph write "who can stop it" and "what counts" into its structure?

This is where a graph pulls away from a pure loop. In a loop, whether to stop and what counts as done basically relies on the model's own judgment; you can only advise in the prompt. A graph turns these into hard constraints in the structure: an edge only opens after human approval, a node output that violates the structure gets stuck and redone, a convergence point proceeds only after collecting N copies. Leaving who can stop it and what result counts to the model's improvisation is too risky; a graph turns them into hard constraints. Controllability thus shifts from hoping the model does it right to forcing it right in code, which is also why flows involving external actions, money, and compliance feel safer to ship as graphs than loops. In a graph every node is named and every transition is logged, so you can trace exactly what happened in any run, who stopped it when, and what result counted. That is what a loop cannot give and a graph forces right. A loop presses these rules into the prompt, and whichever time the model misreads, it leaks; a graph fixes the rules into the structure, and as long as the structure stands, it does not leak.

## 33. Can a graph contain both automatic branches and human gates at the same time?

Yes, and this is the norm in production graphs. Automatic branches handle rules that can be hard-coded: classification result decides which processing line, parallel fan-out does independent sub-tasks. Human gates sit on risk points: before an external action, before charging, before the final draft to the user, someone must nod. The two coexist in the same graph; edges handle automatic routing, nodes or constraints handle the human checkpoint. By design, place the human gate before the side effect happens, not after. The separation of decision and execution also shows here: rules that can be hard-coded, like classification, take the automatic edge; actions with external consequences, like sending messages, charging, and producing the final draft, get a human node in front. A graph with only automatic branches and no gate can only rely on the model to save exceptions; a graph with gates placed upfront intercepts exceptions before they cause consequences. Gate upfront, and the exception dies before consequences occur; gate afterward, and what you intercept is already-sent bad news, too late. After a human reject, which step to return to must be drawn on the graph, otherwise the approval node becomes a dead end and the flow jams with no one to take it.

## 34. State diffs are recorded at every checkpoint. What exactly do you look at when debugging?

Each checkpoint stores the state snapshot after this step. When debugging you do not stare at the whole graph; what changed between adjacent steps is the point. The diff tells you whether the field the previous step wrote is still there this step, what an agent changed and what it dropped, and where the input state at the stuck step diverged from expectation. Without a diff, you can only reverse-engineer what happened from a large chat log; with a diff, locating the problem becomes from state X to state Y at this step, field Z was lost. Typed state makes each node return a local update to state, so adjacent steps can be compared field by field, making clear which segment changed and which was lost. This turns what an agent actually changed from a black box into a structure change comparable line by line, which is why a graph is easier to debug than a loop. A loop only gives you a flat message history; a graph gives you an execution trail with state, with every step's input and output recorded and replayable.

## 35. Why is a graph's boundary harder to define than the graph itself?

Drawing nodes and connections is easy; the hard part is deciding what the graph's edge touches and what it does not. Draw the boundary too narrow and the graph becomes an island, with external systems it should collaborate with only reachable by the agent reaching out ad hoc, uncontrolled. Draw it too wide and the graph swallows too many responsibilities, and every change to an external interface moves the whole graph. Harder still is the side-effect boundary: which actions are irreversible once fired, sending messages, charging, writing to production databases, must be blocked inside the graph's controlled points; which can be retried freely must be treated separately. The side-effect boundary must be explicit: actions like sending messages, writing to databases, calling external APIs are treated separately, decision and execution separated, checking whether already done before executing, with out-of-bounds actions blocked inside controlled points. A graph's robustness comes from a clear boundary, not just how intricate the internal topology is: what enters the graph, what stays outside, and what side effects are isolated are the questions to keep asking yourself when designing a graph. Outside the graph only put pure queries and harmless operations; any action that, once it errors, has consequences on the outside world must land inside the graph's controlled boundary.
