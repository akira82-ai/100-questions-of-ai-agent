# 第四章 · 验证质量与进阶技巧

很多人读到这里反而更犹豫。前面三章把单循环和图的翻车都摊开了，结果就是：既不敢随便上图，又怕该上时没上。判断本身比画图难，而判断如果变成照抄清单、不动脑子，清单本身就成了新的坑。这一章给的是可操作的方法，不是让你闭眼打勾。

## 56 什么时候该上图，有没有一套能照抄的判断清单？

有一套能照抄的清单，但清单只负责逼你说出理由，决定权不在清单手里。把它当成一组触发器，别当成待打勾的考试，六条不一定要全中。第一步永远是先留在循环：一个目标清晰、配了校验器的单循环，上图就是纯开销。只有当工作真的把单个循环撑破，才去加节点。加节点前先给信号起名字，是步骤需要不同专长、需要真并行、还是需要一个可审计的分支。一个真实信号对应一个节点，凡是循环里能内联的步骤都不是节点。动手前先把边画在纸上：什么是顺序、什么扇出、什么汇聚、那条唯一的条件边或回环边落在哪，画不出来就说明还太复杂。再显式设计在边上流动的状态对象，谁有权写、什么跟着边走，状态漂移是图烂掉的头号原因。给审查节点牙齿：最高价值的节点通常是一个独立的、只读的验证器，由另一个 agent 而非产出方来做。隔离失败，让一个节点出错重试时不污染共享状态。最后再选框架、设花费上限和硬边界。这套清单真正的检验在最后一步的反问：你能把五个节点塌回一个循环而什么都不丢吗？能，就塌回去；不能，才上图。

## 57 沾上几个升级信号，才真的该把 loop 升级成图？

一个真实信号就够了，前提是它真的已经撞到你，不是你想象将来可能有。常见的六个信号是：状态超出了上下文窗口、运行必须扛住崩溃、中途需要人工审批、工作流有并行分支、多个模型或 agent 要协调、执行必须可回放审计。其中任意一条真实发生，循环就不够了。拿退款处理举例，订单 API 大约一成概率超时，重试逻辑如果留在模型推理里，它可能重试十五次，也可能一次失败就放弃并臆造订单状态，这类故障靠循环自己兜不住。反过来，如果你只是觉得多 agent 听起来先进，那一条都不算数。判断标准始终是：你是不是已经为这条信号的缺失付过代价。付过，就上；没付过，先别上。信号出现得比真崩早得多，早到你的 agent 一旦需要记住超出当前对话历史的东西，就该把它拉进一个带类型的字典、显式设计状态，这已经是上图前最便宜的一步。等进程崩溃丢了二十分钟工作才动，成本已经付了。趁早识别，比事故后来补课便宜。

## 58 6 条一个都不沾，我是不是就该老老实实留着循环？

是的，六个信号一个都不沾，循环就是对的工具，图是纯开销。但留循环不等于什么都不做。成本最低的一步是先外置状态：一旦 agent 需要记住超出当前对话历史的东西，就把它拉进一个带类型的字典，定义好字段、类型和默认值，模型不用再翻自己几步前的聊天记录去找订单号。这一步几乎免费，回报却最高，它把循环和图之间的鸿沟填掉一大半。真正的跨步动作是加持久层，让进程崩溃后能带着状态重启，这一步才需要把步骤命名成节点。所以留循环是策略，不是偷懒，先把外置状态做了，等真信号出现再走下一步。很多团队卡在外置状态做了但还不敢上图，这正是对的停法。六个信号没出现，停在结构化状态加强校验器，比强行进图省下大量维护。图不是升级，它是对具体架构需求的回应，停在能解决问题的那一层不丢人。

## 59 现实锚点怎么加，才能让图不会自己骗自己？

锚点是模型无权改写的外部真值源，加法有两种。一种是双写校验：一个节点产出结果，同时去模型改不了的地方核对，不一致就报警，绝不悄悄放行。双写校验要落在证据上，不靠感觉，比如确认测试是真跑过了，而非仅仅假定它会通过。另一种是冻结节点：某些值只能读不能写，像留出不让训练循环看到的测试集、合规硬约束、或者由人来判断什么算更好的判定。锚点的来源必须是模型自己动不了的东西，留存的收入、实物库存、真实的银行存款、冻结的安全规范，或者人对更好的判断都行，模型自己生成的报告不算。锚点之所以可信，正因为它不能被系统自己博弈，像银行里的真金、核实过的留存、实打实的库存计数。没有锚点的图会慢慢漂离现实还觉得自己全对，这就是回声室的活标本。审计循环要定期把指标重新对着这些锚点接地，否则锚点本身也会烂掉，变成一个内部报告照样骗人。

## 60 图搭错了想退回 loop，有哪些明显的退回信号？

第一个信号最硬：一张图从头到尾没有一条条件边、没有一个环，状态也不超出单次运行，拍平成一个顺序函数功能不丢，那它本就是个循环，加图只是多了序列化开销。第二个：调试时发现每条路径都指向同一个过载的校验器，其实你要的是把校验器拆出来，不是上整套图。第三个：协调延迟超过了并行省下的墙钟时间，边的同步成本比任务本身还贵，在实时、亚秒级响应场景里尤其明显。第四个最直接：某个节点存在只是因为图看起来更认真，没有任何信号逼它出现，这种动机跟为了更大的厨房听起来更气派是一回事。这四条任意一条成立，退回循环加个强校验器通常更快更稳。图的价值在于显式结构，结构不带来对应收益时它就是负担。能塌回循环而什么都不丢的节点，本就不该是节点，删掉它系统往往更稳。

## 61 怎么测一张图，不能只测最终答案吧？

只测最终答案等于没测。图要测的是每一层契约。每个节点的输入输出要符合预先定义的状态 schema，边界条件给错了类型会不会崩；每条边的路由对不对，分类器返回有毒时有没有真走到审核节点，绕开了回复节点；状态在每次 checkpoint 记了什么，调试时能不能还原；人工闸门在哪些状态触发，拒绝后回到哪一步；失败路径，重试耗尽、超时、外部 API 挂了分别怎么走；恢复路径，中途杀掉进程用同一个标识重启，能不能从正确的节点接着跑。这些都要有独立用例。节点要写成可安全重跑的，发邮件这类副作用节点在下手前先查我是不是已经发过，避免崩溃恢复时重复发送。把恢复测试接进持续集成，每次改图跑一遍，比靠人肉 review 可靠。图的优点就是轨迹可重放，测试也能重放，这点是循环给不了的。

## 62 为什么只评最终答案会让假成功的系统显得特别强？

假成功是最终结果很漂亮、过程已经烂了。只看最终答案时，一个只消费内部报告的图可以每个内部检查都通过，却已经漂得离现实十万八千里，因为所有检查都是报告对报告，从不对着真实世界。这正是那句一切一致、却什么都没验证的白描。一堆 agent 互相确认、谁都不碰真实世界，垮起来的方式和单个循环一模一样，只是零件更多、更贵。要给这种系统打分，它对最终答案的得分会很高，因为它从不检查过程是靠捷径还是靠正确推理混过去的。破法是绑过程指标：校验器有没有真在判断，锚点有没有被重新接地，副作用有没有去重保护。过程指标一拉出来，假成功的系统分数会塌，真稳的系统分数才站得住。所以评测不能只看输出，要看轨迹。对同一批输入跑新旧两版，对比轨迹差异，比只看分数更早暴露问题，等分数塌了，代价早就付过了。

## 63 评估要绑到真实 trace 上，具体怎么落地？

落地分几步。先收集生产环境的真实轨迹，主流框架都内置 tracing，每节点的输入输出、耗时、花费都记下来，这些记录是控制流显式化带来的后果，不是事后外挂。再从这些轨迹里抽难例建回归集，不要只靠合成数据，合成数据跑久了会脱离真实流量，分数却还在涨。然后给每个节点写断言，输出 schema 对不对、不变量成不成立，比如审批状态只能是待审、通过、拒绝之一。接着跑新版本对照旧版本，看哪些轨迹的行为变了、变了是不是更好。最后用固定基准覆盖边缘情形，离线红队测的是质量不是分数，基准要包含那些出错代价高的样本。绑了真实 trace，评估才是在量真实世界，不是量自嗨。trace 也要防漂，审计循环定期用真实新流量刷新回归集，否则半年后你的真实基准又成了合成数据。

## 64 状态超窗、要扛崩溃、要中途审批，这三条怎么排优先级？

优先级看的是出错的代价，实现难度不重要。状态超窗排最高，因为它直接决定正确性：上下文塞不下时，模型会去翻自己更早的推理来算一道简单算术，这时候它已经开始臆造订单状态，结果就是错的，后面再稳也没用。中途审批次之，涉及钱、外部动作、合规的步骤必须有人点头，错了是对外界有后果的，比如合规工作流在采取外部动作前必须审批。扛崩溃排在最后，它解决的是丢了怎么办，一个跑了二十分钟的工作白跑确实痛，但前提是前面两步的结果本身是错的或未经授权的，丢了反而可能是及时止损。顺序是先保证正确、再保证受控、最后保证不丢。如果资源有限只能先做一件，先做状态外置，把超出对话历史的东西拉进带类型的字典，这件事不依赖图的完整结构，循环里也能起步，却已经挡掉大部分失真。

## 65 并行分支和动态转移，是不是上图最硬的理由？

是结构上最硬的理由，因为这两件事循环在定义上做不到。循环是顺序的，一次只走一条路，要同时查多个文件只能排队，墙钟时间就是全部成本；图能把独立子任务扇出到多个节点并行，再汇聚结果。动态转移更极端，循环没法在运行时决定要起多少个 worker，orchestrator-workers 那种由中枢按具体输入动态拆分任务的方式，循环只能写死上限，图能用一个节点在运行时把工作动态发给下游。但这只是循环做不到，不是值得的充分条件。并行和动态都成倍放大测试面和可能的执行路径，每加一条条件边，可走的路就多一截。得先算协调成本能不能被并行省下的时间买回来。做不到是上图的必要条件，不是免思考的通行证。一个判断法：先算并行省下的墙钟值不值同步成本，再算动态转移的 worker 数是否真随输入变化，数量稳定就写死静态边，别为用不上的灵活性付出不确定性。硬理由成立时，图确实是最干净的载体。

## 66 可回放审计为什么成了上图的刚需而不是加分项？

监管和高风险场景必须能回答这次为什么走 A 不走 B，这是合规底线，不是锦上添花。循环只留下一条扁平的消息历史，事后想还原哪一步调了哪个工具、花了多久、谁批准的几乎不可能，因为路径是涌现的、没被显式记录。图把每个节点命名、每次转移记入日志，运行时长、花费、顺序全有结构化轨迹，配合 checkpoint 还能回放整段执行。这套能力来自把控制流显式化，不是外加的监控。金融这类场景里，涉及资本或拒绝客户的决定不能交给不透明的自动机，生产系统里约六成带人工介入点，金融里这个比例更高，就是监管原因；合规工作流在采取外部动作前必须审批，没有审计踪迹就过不了关。所以可回放从加分项变成了门槛。选不选图可以讨论，要过审计这条线，图的轨迹基本绕不开。即便不用完整图，至少把关键步骤的进出记成结构化日志，事后能还原，这比纯消息历史强。审计要的是可追溯，图是最省力的实现，不是唯一实现，但完全不记轨迹在合规场景下过不了关。

## 67 图的开销除了钱，还有哪些隐性成本没人提？

钱只是最显眼的。延迟上，每个 checkpoint 是一次数据库写、每条条件边是一次函数调用、每个节点边界是一次序列化反序列化，五节点 Postgres 图每次运行比裸循环多大约十到五十毫秒，实时、亚秒级响应的场景就敏感。协调开销，并行要同步点、错误处理成倍，一个分支失败可能或可能不影响其他分支，逻辑都得你写。调试复杂度，三个条件边能组合出最多八条路径，每条都要测。状态设计，每个字段要类型、默认值、reducer，schema 错了全图类型报错。还有失败面更多，重试、兜底、超时都是循环版本不需要的新代码。图更可靠，恰恰因为它不把编排信任交给模型，但那份可靠是用工程工时换来的。图的优点省下的是运行时的不确定性，摊开的是人和维护的长期账，算总账时才看得清。

## 68 我怎么向团队证明上图值得，而不只是听起来高级？

靠指标说话，不靠听起来高级。算失败恢复时间，循环崩溃丢了二十分钟工作，图的 checkpoint 能带着状态从断点重启；算并行省下的墙钟，多个文件顺序跑对比扇出汇聚；算审计能不能过合规，这是能不能上线的硬条件，图的每条转移都有结构化轨迹可重放；算调试定位时间，一条扁平 transcript 对比能二分排查的分布式执行。把账算清楚还要看花费，每个节点记录输入、输出、时长和成本，没有 tracing 的话一次运行花了多少钱直到账单出来都是谜，慢节点也找不到。把这些数字摊开，对照判断清单逐条点名是哪个信号逼出来的节点，团队看到的就不是名词，是对应问题的解决成本。证明上图值得，靠的是证明循环已经为某个信号付过代价，图更时髦这件事帮不上忙。撞到代价的人讲自己的事故，比任何架构图都有说服力，数字和事故会替你说话。

## 69 什么时候图反而拖慢交付，宁可先用 workflow？

流程结构在写代码时还定不下来的时候，图就是负担。规划、委托、上下文管理是涌现的开放任务，硬塞进静态边的图反而错，正确做法是留在更 agentic 的 harness 里让结构自己长出来。图适合结构已知的任务，比如分类、检索、合成三段固定，边早就清楚。如果你的流程每周改一次结构，图的静态边每次都要动，而 workflow 的降级版，顺序、并行、路由，已经够用，就先用 workflow。Anthropic 的经验是先试单 agent，步骤只是 prompt 的一部分，够好就别拆；拆成多步只有当单 agent 稳不住时才做。图是 workflow 的上层，下层够用就别爬。判断标准很朴素：你这周改流程结构的频率高不高？高，就别把结构焊死在静态边里；低，图才值得。结构稳定是图的前提，不稳定时 harness 和 workflow 反而更轻，硬上图是把变动焊进编排里，改一次痛一次。

## 70 判断该不该上图这件事本身，有没有反模式？

有，而且比画图的反模式更隐蔽，因为它发生在动笔之前。第一种是把六个信号当机械打勾，不看是否真撞到，清单成了免思考的护身符，记住那张表是一组触发器，不是待满足的待办。第二种是过度谨慎的反面，明明有信号还赖在循环里，靠更长的 prompt 掩盖，结果校验器过载、重试逻辑塞进模型推理，这正是模型自己决定重试时会调用坏工具几百次、毫无停止条件的由来。第三种是过度激进，为显得先进硬上图，节点因为图看起来认真而存在，可大多数任务根本不需要图，硬上只是烧钱加失败面。第四种是只看 demo 不看生产轨迹，有三种模式在 demo 里好看、上规模就塌，demo 跑通和半夜图跑飞是两件事。第五种最省事也最危险，用流行度替你做判断，把图工程当成新名词就跟风，可命名一个新词不等于发明新技术，说不清什么算做对了且正确，再漂亮的拓扑也是更体面的失败。判断的反模式本质都是同一件事：把该不该上图的答案交给了别人，而非交给你实际撞到的失败。破法也朴素，每次想上图或留循环，逼自己写一句我撞到了什么具体失败，写不出就先别动。
