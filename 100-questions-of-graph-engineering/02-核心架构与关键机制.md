# 第 2 章 · 核心架构与关键机制

上手写第一张图的人，多半先在节点和边之间犹豫。节点放什么、边连到哪里、状态怎么传，这三个问题没想清楚，后面每加一个 Agent 都是在给混乱加码。这一章不堆名词，把图的骨架拆开讲：节点、边、状态各自管什么，为什么缺一个都不行，以及生产里那些看起来高级的图，底层其实还是这几样东西在转。

## 16 为什么图的节点、边、状态缺一不可？

节点负责干活，一个节点可以是一段确定代码、一次模型调用、一个工具调用，也可以是一整个带自己循环的子 Agent。边决定走完这一步去哪，有的写死成确定路径，有的看节点结果或当前状态动态选。状态是流经全图的信息，每一步读它写它，它也是贯穿全图的 typed 字典，每个节点都能读写，运行时负责排序、存盘与恢复。三者分开看都简单，合起来才是一张能跑的图：只有节点没有边，系统退化成一堆互不调用的孤立函数；只有边没有节点，路径再漂亮也没东西执行；状态缺席，每一步都从零开始，重试、续跑、审计全没支点。图把做什么、按什么顺序、带着什么信息同时固定在结构里，缺一件就退回普通脚本。把图当状态机看，它定义工作流、在其中流动的状态、以及步骤之间的转移，三者缺一不可。

## 17 都说 Loop 是简单图，它到底简单在哪又缺什么？

一个单 Agent 循环，就是一张有向有环图：节点是思考加动作那一步，边把它连回自己，loop 是 graph 的最小形态，不是它的对手。它简单在只有一个节点、一条回边，不用设计分支和汇合，不用想谁传给谁。缺的是把多个不同工作单元摆成网络的能力：loop 定义上就是顺序的，一次只能在一个上下文里转，没法让子任务并行扇出，没法让不同专家各管一段，也没法在中间某步卡一道人工审批。当你需要一张结构来规定谁在什么时候对什么点头，loop 给不出这种骨架，只能靠模型临场发挥。图形框架里，一个节点的回边就构成 loop，只有当它需要并行、审批、按步换模型时，才值得扩成多节点图。判断该不该从 loop 升图，看任务是否真的跨了多个需要分别约束的单元：独立并行的分支、按步用不同模型、中途要人审批，命中任何一条才上图，否则 loop 足够。

## 18 DAG 和有环图到底该用哪个，图一定要无环吗？

不一定无环。DAG 适合一条线走完不回头的工作，先分类、再检索、最后综合，每步只向前。但系统一旦要重试失败的工具调用、向用户追问缺的信息、校验后返工、或者暂停等人输入再继续，它就必然带环。生产 Agent 几乎都要循环：重试、追问、返工、等人输入再继续，这些动作无环结构装不下。选 DAG 还是含环图，看流程会不会回头，纯管道用 DAG，凡是带再来一次或等人的就接受环。硬把含环流程塞进 DAG，循环只会藏进某个节点内部，真正回路埋进实现细节，结构图上反而看不出来，也更难调。无环只是拓扑排序排完就完事，带环才容纳 Agent 系统的核心动作，先问流程回不回头，再定图要不要环。DAG 适合先分类再检索最后综合这条线，含环图才装得下 Agent 系统的循环动作。

## 19 为什么生产里的图往往不是 DAG，而教科书总教 DAG？

编译原理、数据处理常把任务建模成 DAG，依赖排好拓扑序就完事，无环意味着无死锁、易并行。但 Agent 的下一步常常来自运行时判断，不是静态依赖。追问用户、重试、返工、等人审批，这些动作 DAG 装不下。生产里的 Agent 图通常不是 DAG，因为循环是 Agent 系统的核心动作。图不必是 DAG，它容纳循环，本质是一个允许回路的状态机：图定义工作流、在其中流动的状态、以及步骤之间的转移，回路是其中的合法成分。把循环当一等公民，才能如实表达 Agent 系统的真实行为，否则循环只会被塞进某个节点的内部，结构图上看不见，也难调。教科书给你干净的思维模型，生产逼你接受带环的现实，区别就在下一步来自静态依赖还是运行时判断。

## 20 确定性路径和 agentic 步骤怎么在同一个图里共存？

一张图里，确定步骤和模型自主步骤可以并处，关键是谁在哪一格做主。固定操作写成确定节点，模型只在需要判断的地方出手：分类用一次不带工具的模型调用，综合用一次生成，开放探索交给带自己循环的子 Agent。模型推理出现在它真正加分的地方，其余交给代码，系统因此更便宜、更快、更可预测。一个文档 Agent 的例子里，拉取请求和线性操作由固定代码与 API 调用驱动，分类和综合用单次模型调用，参考文档和概念文档两个子 Agent 做开放式工作，三者在同一张图上各司其职。不同步骤用不同模型也是同图共处的常见做法：检索用带搜索权限的模型，起草用大上下文窗口的模型，复核用便宜快速的模型。同一张图里检索、起草、复核可以分别用不同模型，这正是确定与自主混排的样本。

## 21 状态为什么要做成 typed 结构，而不是塞进聊天记录？

把状态塞进聊天记录，等于让每个 Agent 从一大段自然语言里自己猜上一步给了什么。字段名会变、类型对不上、格式漂移，下游只能靠重建含义，错了还难定位。类型化状态把每步之间传递的数据形状固定下来：哪些字段、什么类型、允许哪些值，都写进结构。不符合结构的数据在边界就失败，而不是流到后面悄悄污染，调试也从翻日志猜意思变成这条 payload 违反了哪条结构。在多个 Agent 之间，typed 状态让每个节点读它需要的、写它产出的，状态替代了指望模型回忆几步之前发生了什么。typed 状态还要求每个字段有类型、有默认值，多个节点写同一字段时要定义如何合并，把 schema 定错会在每个节点都撞上类型错误。状态显式成 typed 结构后，重试、续跑、审计才落得到具体字段上，这是图能像程序一样可靠的前提。

## 22 条件边怎么写才不会退化成一堆 if else 嵌套？

条件边和 if else 的区别在落点：if else 把分支逻辑散落在代码里，图把什么情况下走哪条路收进边本身。写法上，别在节点里写一堆判断再手动跳，而是让边读状态或节点结果，返回一个目标节点名。条件边正是一个检查状态、返回下一节点名的路由函数，分支就活在边里而不是节点里。这样分支可见、可测、可在观测面板里画出来。确定边永远通向同一个下一节点，条件边才运行路由函数检查状态返回下一节点名，两者分开，结构图才能独立讲清走向。退化成 if else 嵌套的信号是：你改一个分支要同时动好几个节点的内部代码，而且没人能只看结构图就说出流程。边承载条件、节点只管干活，职责分开，路由逻辑不再散在节点内部的 if 里。条件边可以基于节点结果、当前状态或外部信号来选下一节点，选路逻辑从此留在边这一层。

## 23 子图拿来封装专家内部流程，什么时候该用？

当一个子 Agent 的内部流程复杂到值得单独成块，就把它封成子图。外层图只关心把任务交给它、拿回结果，不关心它内部怎么转。主管- worker 模式常实现为 subgraph：主管分解任务、路由给专门的 worker 子 Agent，worker 的内部步骤被封装起来，对外只暴露输入输出。子图内部自洽、外层保持扁平，接口只暴露输入输出，复用、测试、恢复点都能单独加在这一块上。该用的信号是这段流程被多处复用、内部步骤常变但对外契约稳定、或者你想单独给这块加测试与恢复点。不该用的信号是它只被调用一次、内部就一两步，封起来只是多一层间接。子图是给复杂度付账的工具，不是默认动作，用错地方反而增加认知负担。封得对，外层读图像读一句功能说明；封得错，反而多一层要猜的间接。

## 24 动态转移解决的是什么，普通边做不到吗？

普通边在画图时就定死了：A 连 B、B 连 C。但有些工作，下游节点数量要等运行时才知道。典型是分治：把输入拆成几块，每块发给一个工人，再汇总，而块数取决于输入本身。动态转移让一个节点在运行时决定发多少份工作给哪些下游，连接不写死。它解决的是已知结构、未知规模的活：你知道要扇出再汇总，但不知道扇出多大。没有它，你只能给一个保守的固定上限，浪费或者不够都在所难免。图形框架用 Send 类的原语让节点在运行时把工作动态路由到一个或多个下游，不必静态写死每条转移。代价是终止和聚合逻辑要自己写清楚：扇出何时算完、汇总前要不要去重，静态图替你想好，动态的得你定。研究类任务常先扇出再综合，但到底要扇出多少个事先未知，正是动态转移的用武之地，静态边只能近似。

## 25 为什么状态要跨运行共享，重启后图还能接着跑靠什么？

Agent 跑到一半进程挂了，重启后不该从头来。靠的是把状态外部化：每走一步，把当前状态写到一个进程外的存储，下一步从那里读。检查点就是每步执行后存下的状态快照，进程崩溃就从最近一个检查点接着跑。跨运行共享还意味着多实例、人工隔了几天再回来，都能接上同一条状态。代价是要设计清楚存什么、多久存一次、恢复时怎么跳过已经做过的副作用。把状态留在记忆里，重启即失；把状态外置，图才第一次有了暂停等人接着干的能力，这也是图能跑长任务的前提，loop 很难天然具备。外置的持久层本身要可靠，用会丢的记忆缓存放状态等于没外置；生产里常用 Postgres 或 Redis 这类进程外存储做检查点后端，内存缓存在测试之外不该用于生产。

## 26 人工审批在图里是一个节点还是一条边，差别多大？

它既可以是节点也可以是边，差别在语义。作为节点，审批是一个明确的工序：人到这一步，看了，批了或拒了，流程继续，它在结构里占一个可见的位置，能被观测、被计账、被跳过逻辑识别。作为边，审批是走这条路之前必须有人点头的约束，更轻，不占独立工序位。需要问责和可观测的环节，优先做成节点，让审批在图上一眼可见。人工闸门作为中断点让图暂停、等外部输入，状态留在库里，进程可以整个关掉，人回应后再从同一检查点继续。轻量提示类确认用边就够了，涉及钱、外部动作、合规的，做成节点，留下可追溯的脚印。生产里更常把它当节点，因为你要能说清楚卡在谁那、卡了多久、为什么拒，这些只有节点位才承载得了。审批作为节点时，卡在谁那、卡了多久、为什么拒都能从结构里直接读出，问责和可观测才落得住。

## 27 谁来决定下一步走哪条路，是模型还是我？

这张图里，有些路由你写死，有些交给模型。确定路径写死，省得模型每次重新猜；需要判断的分支，让模型按状态选。分工的原则是：凡是能提前说清规则的，就用代码定，别赌模型每次都对；只有真正依赖上下文、无法硬编码的，才让模型决策。该让模型做主的地方让它做主，该强制确定行为的地方强制，而不是指望模型每次都做对。路由函数检查 retry_count 超过阈值就转去错误处理，检查 approval_status 通过才继续，或看分类结果把任务送到对应专家节点，这些都是代码定规则而非模型临场决定。全写死失去灵活性，全交给模型失去可控性，平衡点就是这张图的骨架。把哪步让模型决定、哪步写死当成设计变量，是图比纯 loop 更可预测的原因：编排不交给模型临场发挥。

## 28 主管、层级、群体、扇出汇聚这几种拓扑怎么选？

四种常见摆法对应不同协作方式。主管把任务拆给专家再收结果，适合能清楚拆成子块的任务；层级是主管的推广，多层嵌套，适合大任务分多层。群体是 Agent 平级在共享黑板上读写，适合探索型、事先不知道怎么拆的活，但容易漂。扇出汇聚是先并行铺开再合成，适合互相独立、可并行的子任务。生产里默认在主管和图之间选：任务分解清楚用主管，控制流带条件、要可观测用图。主管- worker 和图是生产里真正划算的两种多 Agent 模式，群体与黑板模式理论上有趣却很少胜过前两者。群体只在探索或研究模式用，不进生产主线，因为缺了主管锚点，目标容易失焦。主管几乎总在生产里胜过群体，因为主管锚定了目标对齐，群体没有锚点就会漂。层级是主管的推广，适合大任务分多层。

## 29 为什么选错拓扑常常比选错框架代价更高（但也别忽略框架锁死的长期成本）？

拓扑定的是协作结构，框架只是实现它的工具。一个用群体却需要强目标对齐的系统，会因为缺少主管锚点而漂，换哪个框架都救不回来；反之框架选错了，多数模式都能在别家重写，迁移有成本但不是结构死局。先定拓扑再选框架。但框架锁死是真实长期成本：一旦生产化，图的状态格式、持久层、观测都绑在一家，重写代价陡增。框架已经趋同支持这些标准模式，换框架重写的代价通常不合算，所以拓扑优先想清，框架只当执行引擎。别为了躲框架绑定就牺牲结构正确性，也别沉迷选型忽视锁死。多 Agent 模式在主流框架里都支持，选框架看团队熟悉度和运维集成，不看哪家独有能力。模式在各个框架间是通的，换框架大多只需重写执行引擎，不必推翻拓扑。拓扑错了是方向性问题，框架错了是工程性问题，两者都要防。

## 30 图的可恢复在原则上恢复的是什么，节点、整条状态，还是两者之间的某一层？

原则上恢复的是状态对象，不是节点也不是整张图。节点是无状态的计算单元，给定输入就产出输出，单独恢复它没意义；整张图重跑又太贵，而且副作用会重复。真正要存的是每一步之后的状态快照：崩溃后从最近的快照读回，重放还没做的那几步。中间那一层是副作用边界：已经对外部世界做的事，发了消息、扣了款，不能靠重放补，得用幂等键跳过。副作用隔离的稳妥做法是把决定与执行分开：决定节点说应该发、执行节点发之前先查是否已发过，这样决定节点可安全重放，执行节点靠幂等键避免重复。难点从来不在存快照，在隔离那些存不回去的动作。幂等键是副作用隔离落地的具体做法，它在执行前先查是否已做过，保证崩溃恢复时同一条消息只发一次。把副作用边界划清楚，恢复才是干净的重跑，而不是灾难的复播。

## 31 多个 agent 共享状态对象和互相传消息，差别在哪？

共享状态对象是多个 Agent 读写同一块结构化数据，谁改了什么一目了然，适合需要一致视图的协作，但要有并发控制，否则两个 Agent 同时改会互相踩。互相传消息是每个 Agent 只给自己下游发一段内容，耦合更松、更像一个流水线，但全局视图散落，谁都看不到全貌，排错要靠把消息串起来。差别在共享内存还是传信：共享状态强一致但易冲突，传消息松耦合但难追溯。没有共享状态的多 Agent 像接力赛，每一棒都不知道前一棒往哪跑。复杂协作里常两者混用：共享状态存真相，消息驱动流转，当你开始用消息内容去重建现在全系统什么状态，说明该上共享状态了。并发写同一字段要加锁或约定归属，否则后写覆盖先写，谁改了什么都难追。给每个节点单独配工具权限，是避免共享资源竞争的一种落地办法，让并行节点不抢同一份外部资源。

## 32 为什么图能把谁喊停、什么算数写进结构里？

这是图和纯 loop 拉开距离的地方。loop 里停不停、什么算完成基本靠模型自己判断，你只能在提示里劝。图把这些变成结构里的硬约束：某条边只有在人工批了才通，某个节点产出不符合结构就卡住重来，某个汇合点收齐了 N 份才往下走。谁有权喊停、什么结果算数，靠模型临场判断风险太高，图把它们落成了硬约束。可控性因此从希望模型做对，变成代码强制做对，这也是为什么涉及外部动作、钱、合规的流程，图比 loop 更让人敢上线。图里每个节点有名、每次转移有日志，能追出任意一次运行到底发生了什么、谁在何时喊停、什么结果算数，这正是 loop 给不出、图强制做对的原因。loop 把这类规则压在提示里，模型哪次没读懂就漏了；图把规则固定进结构，只要结构在就不会漏。

## 33 一张图里能不能同时有自动分支和人工闸门？

能，而且这是生产图的常态。自动分支处理能硬编码的规则：分类结果决定走哪条处理线，并行扇出做独立子任务。人工闸门卡在风险点上：发外部动作前、扣款前、给用户的终稿前，必须有人点头。两者在同一张图里共处，边负责自动路由，节点或约束负责人工卡点。设计上要把人工闸门放在副作用发生之前，而不是之后。决策与执行分开也体现在这里：分类这类能硬编码的规则走自动边，发消息、扣款、出终稿这类对外有后果的动作前面卡人工节点。一张只有自动分支没有闸门的图，遇到例外只能靠模型救；把闸门前置的图，例外在造成后果前就被人拦下。闸门前置，例外死在后果发生之前；闸门后置，拦下的是已经发出的坏消息，为时已晚。人工拒绝后该回到哪一步，要在图上画出来，否则审批节点成了死胡同，流程卡死没人接。

## 34 状态 diff 在每次 checkpoint 记录，调试时到底看什么？

每次 checkpoint 存的是这一步之后的状态快照，调试时不用盯着整张图，相邻两步之间状态变了什么才是重点。diff 告诉你上一步写的字段这一步还在不在、某个 Agent 改了什么漏了什么、卡住的那步输入状态和预期差在哪。没有 diff，你只能从一大段聊天记录里反推发生了什么；有 diff，问题定位变成从状态 X 到状态 Y 这一步，Z 字段丢了。typed 状态让每个节点返回的是对状态的局部更新，因此相邻两步之间能逐字段比对，哪段改了、哪段丢了都看得清。这一步把 Agent 到底改了什么从黑盒变成可逐行比对的结构变化，是图比 loop 好调的原因。loop 只给你一条平直的消息历史，图给你带状态的执行轨迹，每一步的输入输出都有记录可重放。

## 35 为什么图的边界比图本身更难定？

画节点连线容易，难的是决定图的边缘接什么、不接什么。边界定窄了，图变成孤岛，该协作的外部系统只能靠 Agent 临时去够，不可控；边界定宽了，图吞进太多职责，每改一个外部接口就要动全图。更难的是副作用边界：哪些动作一发不可收，发消息、扣款、写生产库，必须挡在图的受控点内；哪些可以随意重试，要分开对待。副作用边界要显式：发消息、写库、调外部 API 这类动作单独对待，决定与执行分开，执行前先查是否已做过，越界动作被挡在受控点内。图的健壮性来自边界划得清，不单看内部拓扑多精巧：什么进图、什么在图外、什么副作用被隔离，是设计图时最该反复问自己的事。图外只放纯查询和无害操作，一旦出错就对外界有后果的动作必须落在图的受控边界内。
