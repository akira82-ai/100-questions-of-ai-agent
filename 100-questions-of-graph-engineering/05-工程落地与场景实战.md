# 第 5 章 · 工程落地与场景实战

图在纸上画得再漂亮，跑起来是另一回事。这一章把前面四章的判断变成可操作的工程动作：状态怎么定、检查点落哪、人工在哪拦、副作用怎么关进笼子、半夜跑飞了拿什么排查。读者最该带走的一句话，是工程纪律而非某个框架名，它比框架选择更决定生死。下面每题给一个能直接照做的机制和至少一个踩过的实例。

## 71 状态 schema 怎么设计，才不会每次改字段就崩全图

状态用强类型结构在节点之间传递，每个节点收到它、返回局部更新，框架按你定义的规则合并。规则里最要命的是 reducer。一个并行字段若没有 reducer，七个节点同时写它，最后只剩一个随机节点的结果，其余六份静默丢失，图跑完交付的报告干脆缺了六个因子，这种错没有堆栈可查。给这个字段挂上累加 reducer，写操作就变成累积、不再覆盖，并行分支的产出才保得住。另一个坑是把什么都能往状态里塞，原始 dataframe、整段模型响应全进去，结果每个节点拖着几兆只为了读三个字段，检查点也跟着膨胀。做法是状态只放多个节点真正需要共享的东西，重对象留在存储里，状态存引用。顺序上先定类型和并行字段的 reducer，再写节点，这一步能拦掉后面大半的结构性故障。

## 72 checkpoint 应该设在哪，是不是每个节点都该是恢复点

检查点把每个节点之后的状态写进持久层，靠一个运行标识来恢复，进程死了、服务器重启了都能从原地接上。每个节点都设是合理的默认，但检查点只是恢复机制，不是预防机制。它把你送回节点倒下之前的状态，却拦不住节点因为同一个原因再次倒下。一个节点命中限流失败，从检查点恢复会原样复现这次失败。真正的防线在节点层：限流、并发上限、指数退避、必要时降级到缓存。每个节点都设检查点该做，但别当免死金牌，节点级失败处理才是让图在单点出问题时整体不垮的东西。预算允许的话全设，关键是恢复之后失败仍要在节点内被接住，否则只是延后了同一处爆炸。一个判断信号：某节点反复倒下时，你是在修节点还是只在重试，这决定了检查点到底在帮你还是只是延后爆炸。

## 73 崩溃后从 checkpoint 恢复，恢复的是消息历史还是整个状态对象

崩溃后恢复的是整份状态对象。强类型状态里装着已累积的字段、计数、各分支的产出，重跑时这张对象是续跑的基底，不是重新拉一遍对话记录。这里要和幂等键配合才稳。图从检查点恢复后，如果某个节点含对外副作用，重跑可能重复发信或重复扣款，得靠幂等键兜底：每个对外动作带一个业务唯一键，节点重放时凭这个键认出已经做过、不再重复。状态对象负责把进度接回来，幂等键负责让重跑不产生二次后果，两者分工才完整。检查点只把进度接回来，节点若带对外副作用，恢复时仍会被原样重放，幂等键就是拦在这一道。一个常见误配是只做检查点不做幂等，结果崩溃恢复一次就多发一封邮件，查起来还以为是邮件系统抽风。这一题是操作层，概念层为什么恢复值得做、恢复哪一层，留在前面章节讲过了，这里只管具体怎么接。

## 74 人工闸门怎么分级，哪些步骤才真的需要人点头

真正需要人拦的是三类：执行交易或动用资金之前、合规流程里拒绝客户之前、任何回滚代价高于等待的动作之前。其余一律自动化，别滥加人工节点把流程拖成橡皮图章。技术上是中断机制，节点抛出一个中断，状态落进检查点、执行结束，进程可以死、服务可以重启，人回答之后凭运行标识从原地带着答案续跑，这和代码里的阻塞等待是两回事，后者扛不住一次部署或一次崩溃。给人的内容也有讲究。中断里别塞原始状态转储，要带一段压缩的决策摘要：提议做什么、依据什么、哪些备选被否了。给人看一大段原始状态转储，他多半不看就点通过，控制点形同虚设。金融场景里审批必须带暴露敞口、最大持仓、用到的因子清单，人才能真做判断。给审批节点的内容把关，比加多少个审批节点都重要，控制点一旦变成橡皮图章，整张图的合规价值归零。

## 75 幂等键怎么加，重试十次也不会重复发邮件

幂等键是动作的唯一业务标识，在调用外部系统之前注入，让同一次动作无论被重放多少次只生效一次。做法是给每个对外动作一个稳定且唯一的键，节点每次执行先检查这个键是否已经做过，做过就不再重复。图框架本身不替你发这个键，得在你写外部 API 调用的那一层手动带上。判断标准很直接：凡是对外有后果的动作都必须带键，图内纯计算不需要。重复发信、重复扣款这类事故，根因几乎都是副作用节点没有幂等保护，重试或检查点恢复一触发就多来一份。崩溃恢复和重试都会重放带副作用的节点，幂等键让重复的那次在节点层被吸收，节点是否重跑都不产生二次后果，这是比赌它永远不重跑更稳的兜底。一个信号是，当你开始担心"检查点恢复会不会又扣一次款"，说明这个动作早该带键了，别等事故后才补。

## 76 副作用怎么隔离，不让图随便重跑就出错

做法是节点不向外抛异常，只返回一个带标记的结果，比如通过或失败加原因，让失败限定在节点内部，不拖垮整条流水线。一个因子节点命中限流，它返回失败标记，不向外抛错，校验节点从标记看出少了一个因子并计入，图用剩下的六个因子继续跑完，这条分支自己认栽但不连累全局。副作用本身再套两层保险：一是幂等键，前面讲过了；二是去重，外部动作前确认同一业务键没处理过。把副作用收进图的受控边界，图外只放纯查询和无害操作，一旦出错就对外界有后果的动作绝不放在可能被反复执行的路径上而没有保护。重跑在图里不可避免，崩溃恢复、重试都会重放带副作用的节点，所以副作用要靠幂等和去重吸收重复，不能假设重跑不会发生。副作用节点若既无幂等又无去重，图每重跑一次就多一笔对外后果，这类事故在重试和崩溃恢复场景下几乎必然发生。

## 77 可观测到底要抓什么，为什么只看日志不够

日志只告诉你某步报错了，回答不了半夜告警时你最想问的那串问题：哪个节点在这次调用里做了什么、输入什么、调了哪些工具、中间产出是什么、花了多少钱。每节点抓四项就够地基：输入、输出、耗时、成本。整次运行再汇总一组指标，加上预算超支告警。agent 级的 trace 语义约定经过 2025 年已经成熟，成了事实标准，主流框架几乎都吐 OpenTelemetry 格式的轨迹。只看日志的后果是成本到账单出来才知道失控，慢节点永远找不到。成熟团队能把任意一次生产调用的全貌还原出来，这套埋点不轻松但是必需。可观测是图能在生产里被信任的前提，没有它调试就退化成猜。最起码先把每节点的输入、输出、耗时、成本埋上，这是小团队也负担得起的第一步。

## 78 没有 trace，半夜两点图跑飞了我该怎么排查

三件工具让这种排查可操作。第一是读检查点，状态在每个节点之后都存了，把某次运行的历史拉出来，就能看到在哪一点数据开始变歪，比如因子计数在某个节点之后停止增长。第二是回溯重放，取运行中某个检查点，改一下状态再从那里续跑，不用重跑前面所有节点、也不用为前面那些再付一次钱，用来验证“如果当时校验节点收到的是这个输入，它会不会判对”这类假设。第三是节点追踪，每个节点记输入、输出、耗时、成本，没它一次运行的成本就是个谜，慢节点也定位不到。图的麻烦在于常常没有堆栈：一个节点返回了错的东西，图继续走，错误在三个节点之后才浮上来。图调试靠检查点历史去定位，和脚本靠日志不同，这是两者最不一样的地方。一个被检查点单独抓出的错是并行分支上的竞争：运行完成一个错没有，结果却缺数据，重跑同样输入结果还不一样，没有异常却出现非确定性，几乎总是某次状态更新丢了，也就是忘了给那个字段配 reducer。

## 79 成本路由怎么做，简单 query 别扔给最贵的模型

图的节点不非得跑同一个模型，这是直接撬动成本和质量的杠杆。做法是多数均匀、重复、低判断的节点用便宜快的模型，判断和验证节点用强模型，而且让强模型带着不同指令、只读输出不读生产者的推理过程，避免它确认自己的结论。一个因子分析里七个因子的计算用中等模型，汇总校验用最强模型，因为裁判节点不能是产出者同一个节点，否则自检等于没检。成本上要清醒：一个并行扇出是七个同时发起的模型调用，一个带返回的环把这个数乘以迭代次数。预算必须在运行前算好，不是跑完看账单。实用做法是给每个环硬设迭代上限、给每次运行设成本天花板、逼近上限时降级到更便宜的模型。一个没有上限会自己转的图，总有一天会自己转到破产。成本路由顺带管住了质量：强模型只在裁判位出现，普通节点用便宜模型，裁判不会去确认自己的结论。

## 80 工具调用失败了，退避、重试和熔断该怎么配

节点级的失败处理才是真防线。工具调用失败按这几样配：指数退避的重试、并发上限、必要时降级到缓存。检查点恢复拦不住根因，预防是另一份工作，比如限流失败从检查点恢复会原样复现，必须靠节点内的退避去消解。熔断在失败次数超过阈值时停掉对该工具的调用，这些逻辑写在节点层，不写在图层。一个因子节点命中限流，正确做法是返回失败标记并降级，让这条分支不杀全图；向外抛错会把整个管道带崩，所以不能那么做。判断原则：凡是可能被反复执行且带外部依赖的节点，retry、backoff、circuit breaker 三件套要齐，图只负责在节点认栽时继续往前走，不负责替节点扛失败。缺了任何一样，重试风暴就会把一个 flaky 接口烧光预算，这类事故在并联调用时尤其隐蔽。

## 81 时光回溯调试是什么，为什么图比 loop 更需要它

图的检查点天然带了回溯能力：取运行中某个检查点，改一点状态，从那个点继续跑。loop 重跑只能从头，图可以从中间点续跑，还能改个条件验证假设，不用为前面所有节点再付一遍钱。比如把某个阈值改小，从中点续跑，验证“如果当时校验收到的因子够多，它是不是就直接进组合了”。这一步在图的调试里是核心手段，因为图常常没有堆栈可查，错误在几个节点之后才暴露，回溯加检查点历史是把“数据在哪点变歪”定位出来的唯一现实路径。loop 是单线程，重跑从头代价小，回溯的边际价值没那么高。图是分布式的执行模型，节点错三跳后才显形，没回溯就只能靠猜，图的调试和脚本的调试根本不属同一套工具。回溯还顺带支持了另一件事：图可以完全不调模型就做结构测试，用桩节点验证屏障是否收齐所有并行分支、环是否带上限会终止，这类测试跑在普通 CI 里、毫秒级，能在真实运行花真金白银之前抓出最贵的那个错。

## 82 选框架时，编排模型和耐用层该不该分开看

该分开看，因为两者解决的是不同层级的问题。外层是耐用执行层，负责进程跑几个小时、跨好几个外部服务、扛得住崩溃重启和网络抖动，让流程无论如何到达终点。内层是图，负责逻辑：路由、状态、任务内的条件转移。一个跑几分钟、住在一个进程里的图，内置检查点就够了，外层是多余复杂度。一旦流程要过夜、要碰多个系统、要在基础设施重启后活着，行业做法是两层叠放：外面 Temporal 这类耐用层，里面图。分工很清晰，外层管“能不能走到头”，内层管“这一步怎么走”。判断依据是运行时长和跨服务需求，不是框架流行度。提前把外层加上去属于为想象中的规模付税，等真需要时再引入更划算。一个经验线：单次运行在分钟级、所有动作在一个进程内，内置检查点已经够；一旦要跨夜、要碰多个外部系统、要在基础设施重启后活着，外层耐用层才从nice-to-have变成必需。

## 83 LangGraph、OpenAI SDK、ADK 到底差在编排还是生态

差在两个层面，编排范式和生态承诺都在起作用。一类走图式有状态工作流，给每一步精确控制，分支和错误处理都在你手里。一类走轻量多智能体原语，agents、handoffs、guardrails 几个积木，把控制权换成了简单。还有一类是工作流运行时加任务接口，层级树加 agent 间委派，原生绑定自家模型。角色式 crew 又是另一条路，给每个智能体一个角色让它协作。核心范式差异决定你能不能审计、能不能确定性复现。生态承诺比一年前更重，一旦选定云厂商，切换成本很高。没有单一最优解，按语言、生态、控制需求选。框架真正赚到位置，是在你需要耐用状态、重试、多智能体委派、人工介入、一致追踪这些的时候，简单场景一个模型加工具循环就够了。选型的另一半是团队：纯代码方案在工程重的地方反而跑得最顺，因为它不挡你自定义图的任何细节；角色式框架在想快出活、不想管细粒度控制时最省力，代价是遇到非标准流程时受限。

## 84 小团队没人运维，图的生产化该从哪一步开始

先从成熟模式复用起，别自创编排。编排者加分专家这种形状是生产里最稳的默认，多数企业工作流都吃得下。再把运营纪律补齐，这比换框架重要得多：可观测、成本遥测、评估、灰度发布、SRE 式的事故响应、版本化 prompt。小团队人力紧，优先级是先把 prompt 当生产产物管起来，加基础 trace 和成本上限，这两样几乎零门槛却能拦掉大部分生产事故。不要追最新框架，现有那个能出可接受结果就别动。框架大战到 2026 年已经收敛出可辨认的存活者，多数成熟项目对不同负载用两到三种组合，不是 All-in 一个。小团队最该投资的是纪律不是选型，选型定了之后纪律才是拉开团队差距的东西。一个低成本起步包：版本化 prompt 进源码、基础节点 trace、运行级成本上限、对新配置走小流量灰度。这四样加起来几乎不占人力，却能拦掉大部分生产事故，比追逐新框架实在得多。

## 85 我手头这个场景，第一步该先画状态还是先画节点

先定状态。技术顺序是把状态用显式类型和并行字段的 reducer 定义好，再按数据依赖搭拓扑，再加带环上限的条件路由，再上检查点，再做节点级失败处理，最后才是追踪和预算。每一步拦它那一类问题：强类型状态拦并行竞争，数据驱动的拓扑拦假并行，环上限拦无限循环，检查点给恢复，失败处理拦单点拖垮全图，追踪让调试可能。状态是图的骨架，先划清哪些东西被多个节点共享、共享字段怎么合并，比先画节点更防崩。一个常见征兆是图全无一条条件边、一个环，那它该写成一个普通函数，上图只是多了检查点序列化和一层抽象，没有任何收益。先画状态能让你尽早发现这件事，把图拍平回函数反而更干净。反过来，状态一上来就塞满、reducer 一个没配，也是信号，说明你还没想清楚哪些字段真被多节点共享，这种情况下先画图只会把混乱固化进结构里。
