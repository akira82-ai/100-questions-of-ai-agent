# Chapter 5 · Engineering in Practice: From PRD to Commercialization

## 71. Why is the AI product PRD being replaced by Prompt + Eval Spec? What do the three new requirement docs look like?

The core of a traditional software PRD is describing features: which button the user clicks, what result the system returns, how the flow goes, how state changes. This way of describing starts to fail for AI products, because the core of an AI product is not features but behavior, and behavior is probabilistic; it cannot be described by a deterministic feature spec.

Replacing the traditional PRD are three new requirement docs. The Prompt Spec describes how the model should behave in different scenarios, including role setting, input constraints, output format, exception handling; plainly, it writes a work manual for the model as if it were a new employee. The Eval Spec describes how to judge whether the model performs well, including evaluation dimensions, scoring rules, test-set composition, pass criteria; it writes a scoring standard for the model as if it were an exam taker. The Behavior Spec describes how the model should act in different boundary scenarios, including handling known boundaries, fallback for unknown inputs, confirmation logic for high-risk operations; it writes an authorization boundary for the model as if it were a decision maker. These three docs together are the complete requirement of an AI product.

The traditional PRD describes "what the system should do"; the new docs describe "how the model should act, how to judge it acted right, what to do when facing the unforeseen." If the PM cannot write these three docs, the requirement is not passed clearly; development builds by its own understanding, and at launch finds it completely different from expectation.

## 72. How do you write an Agent's "behavior boundary" clearly in the PRD?

For an Agent product's PRD, the hardest and most important part to write is the behavior boundary. It defines what the Agent can do, what it cannot do, and when it must involve a human; if the boundary is unclear the Agent will run wild after launch.

Writing the behavior boundary takes three layers, tightening from outside in. The outermost is the capability boundary: which types of tasks this Agent is authorized to handle; for example a customer-service Agent only handles consultation, not refund operations; refund tasks go to a dedicated Agent or a human. The middle is the permission boundary: which tools this Agent can call, what the permission scope of each tool is; for example a customer-service Agent can query order status but not modify orders, can initiate a refund flow but not directly execute the refund. The innermost is the risk boundary: in what situations the Agent must stop and wait for human confirmation, usually high-risk operations involving money, data, outbound sending.

These three layers must be written clearly in the PRD, and specifically, not just in principles. Do not write "the Agent should avoid dangerous operations"; write "the Agent must obtain user confirmation before executing the following operations: refunds over 100 yuan, outbound email, deleting user data." The more specific the boundary, the more basis development and testing have; the vaguer, the more likely something goes wrong after launch.

## 73. Should the PRD include the Prompt? If you write it, does development still design?

Whether to write the Prompt in the PRD is one of the most agonizing questions for an AI PM. Write it and you fear development copies it verbatim and stops thinking at the design level; do not write it and you fear development follows its own understanding entirely and the result differs far from expectation. The compromise is to write the Prompt's design intent in the PRD, not the specific wording.

The design intent includes several parts: what role the model plays in this scenario, what task to complete, what constraints the output must meet, how to handle exceptions. The specific wording is left to development or the algorithm team to write and iterate; the PM states the intent clearly, execution to the professionals. The reason for this split is that the Prompt must iterate continuously; after launch it is adjusted repeatedly based on effect data. If the PM hard-codes the Prompt in the PRD, it instead limits iteration room. What the PM should do is define "the standard of good," not prescribe "how to do it."

One more practical point: the PRD should attach a few example dialogues, including typical inputs and expected outputs. These examples are not the Prompt itself, but the effect the Prompt should achieve. Example dialogues carry more information than text descriptions; seeing them, development knows what style, depth, format the PM wants.

## 74. How detailed should an AI feature's requirement doc be? If too coarse, development builds randomly; what then?

An AI feature's requirement doc: too coarse and development builds randomly; too detailed and it is locked with no iteration room. This balance is hard. The principle: write the certain parts in detail, the uncertain parts coarse.

The certain parts are what the PM should decide: business constraints, user scenarios, success criteria, risk boundaries; all must be written in detail. Business constraints include latency ceiling, cost ceiling, accuracy floor; without them development may build for technical optimum and completely miss business requirements. User scenarios include typical user personas, high-frequency usage paths, known boundary cases; without them the product development builds may completely deviate from user needs. Success criteria include how to count success, how to count failure, what the evaluation dimensions are; without them you cannot judge after launch whether it was done well. Risk boundaries include which operations must be human-confirmed, which scenarios must have fallback; without them, when something goes wrong after launch it is a big deal.

The uncertain parts are to iterate continuously: the specific Prompt wording, model selection, retrieval parameters, fine-tuning strategy; write these coarse to leave room. The PM writes the certain parts in detail, and development's execution has boundaries; writes the uncertain parts coarse, and iteration room is kept. If too coarse and development builds randomly, the root cause is usually the PM did not write the certain parts in detail.

## 75. How should an AI product choose its pricing model? Token billing, subscription, outcome-based; how to draw the 5-mode decision tree?

AI product pricing is the most underestimated product decision from 2025 to 2026. Traditional SaaS's per-seat pricing often fails on AI products: one heavy user may consume 100 times the compute of a light user; per-seat pricing turns heavy users into cost black holes. Choosing a pricing model looks at three dimensions: cost structure, user usage frequency, result measurability.

Cost structure decides the broad direction; high-marginal-cost products cannot use per-seat, low-marginal-cost ones can still hold. Usage frequency affects acceptance; high-frequency products users accept subscription or packages, low-frequency products users prefer pay-per-use. Result measurability decides whether you can reach the ideal outcome-based billing; if results are easy to measure you can try it, if hard to measure you fall back to subscription or pay-per-use.

The five mainstream modes each have their fit. Per-seat fits collaborative SaaS, where the main value is multi-user collaboration. Token billing fits API products, where users are developers who understand Token cost. Subscription fits high-frequency C-end products, where users want unlimited use. Pay-per-use fits low-frequency tool products, where users occasionally use once. Outcome-based fits products with clear tasks, where users pay only for completed tasks. The decision-tree logic: first see if the result is measurable; if measurable, prefer outcome-based; if not, see usage frequency, high-frequency use subscription, low-frequency use pay-per-use; if neither, fall back to per-seat. Pricing is not a guess; it is derived from cost structure, user behavior, and result measurability.

## 76. Why do Token-billed products make users want to leave the more they use it?

Token billing sounds reasonable: users pay for what they use, cost aligned with value. In reality this pricing makes users want to leave the more they use it. The root cause is that Token is a unit users cannot understand; they do not know how many Tokens one conversation consumes, do not know how many they will use in a month, do not know what next month's bill will be. This uncertainty makes users anxious; anxious users reduce usage, look for alternatives, run to competitors. Token-billed products have naturally low retention.

Solving this has a few directions. The most fundamental is to translate Token into units users understand; do not show users Token counts, show them "message count," "task count," "document count"; users understand "sent 500 messages this month," not "consumed 500k Tokens this month." Next is to give users a clear quota ceiling: subscription plus quota, overage billed by volume; users knowing their maximum spend lowers anxiety. Another layer is real-time cost feedback: each use, the user immediately sees how much quota this consumed and how much remains; transparent feedback gives the user a sense of control.

Token billing is not unusable, but users must not face Token directly; Token must be wrapped into something users can understand and control. Users willingly pay for value, not for uncertainty.

## 77. Is an enterprise client's "can the model be privately deployed" a real need or a negotiation chip?

PMs of enterprise AI products will surely meet clients asking "can the model be privately deployed." Sometimes this is a real need, sometimes a negotiation chip; you must tell them apart to give the right response.

Real-need cases are several. Industries with high regulatory requirements are real needs: finance, healthcare, government, their data-compliance requirements are extremely strict, data leaving the domain is forbidden. Scenarios with high data sensitivity are also real needs: the client's core data, trade secrets, user privacy cannot be sent to a third-party model. Very large-scale usage is also a real need: the client's call volume is huge, API billing costs far more than self-building; this is an economic consideration.

Negotiation-chip cases also split. One is the procurement process needs it: some enterprises' procurement process requires at least asking about private-deployment options, not meaning they really want to buy. Another is a price-pressing tactic: the client uses private deployment as a chip to force a discount on your API plan. Another is technical curiosity: the client's tech team wants to understand the possibility of private deployment, not meaning the business side really needs it.

The way to tell apart is to ask the client's specific scenario and data volume. Those who can state specific scenario and data volume are usually real needs; those who cannot are likely negotiation chips. Real-need clients deserve investment in private deployment; negotiation-chip clients just need the difference between the two plans explained clearly; do not get led astray.

## 78. What gross margin can an AI product reach, and where is the Token cost floor?

The gross margin of an AI product is a number startups and investors care especially about. Traditional SaaS can reach 70% to 80% gross margin; AI products usually only 40% to 60%, the gap mainly in Token cost.

The Token cost floor depends on three factors. Product type is the most basic: tool-type products' Token cost as a share of revenue is usually 15% to 20%, subscription products 25% to 30%, Agent products 35% to 45%. User structure matters a lot: the cost difference between heavy and light users is huge; 20% of heavy users may consume 80% of Token cost; an unhealthy user structure cannot hold the gross margin. Model selection decides the balance of effect and cost: the most expensive model has high Token cost but good effect; a cheap model has low cost but possibly poor effect.

There are several directions to raise gross margin. Model routing can lower average Token cost: small model for simple tasks, large model for complex. Caching can stop high-frequency questions from burning Token: repeated calls return cache directly. Prompt compression can write prompts more concisely, reducing unnecessary Token consumption. User-tier pricing charges heavy users more, covering higher cost. To reach over 60% gross margin, an AI product must keep optimizing in these directions; without optimization even 40% cannot hold.

## 79. Multi-model routing: how does the PM decide whether a request uses GPT-5 or Qwen-7B?

Multi-model routing sounds beautiful: small requests use a small model to save money, complex requests use a large model to keep quality. In practice, the core problem the PM faces is how to judge whether a request is simple or complex. Judge wrong and a simple request uses a large model, wasting money; a complex request uses a small model and quality collapses.

Judging request complexity has several paths, each with trade-offs. Rule-based is simplest: request length below a threshold, keywords hit certain patterns, user persona belongs to a low-complexity group, use the small model; accuracy is not high but implementation is fast. Small-model pre-judgment is more accurate: first use a tiny model to score the request's complexity; low score goes to small model, high to large; the cost is added latency. History-based is most accurate: how did similar requests perform with the small model historically, with the large model; decide by data; but it needs enough data accumulated first.

Whatever the path, the cost of routing error must be counted clearly. If the routing error rate exceeds 15%, the saved Token cost is offset by quality loss; beyond 30%, model routing is negative optimization. Whether the PM does multi-model routing depends on whether the product's routing error rate can be kept under 15%; if not, better not do it. Model routing is not mandatory; for many products, a single model plus good prompt engineering is more cost-effective than multi-model routing.

## 80. How much Token can caching save, and when is caching instead negative optimization?

Caching is the most direct way for AI products to save Token cost. The principle is simple: users ask many repeated questions; cache the answers to high-frequency questions and return the cache next time instead of calling the model. How much Token caching saves depends on the question repeat rate: customer-service scenarios have high repeat rate and caching saves 40% to 60%; creative-writing scenarios have low repeat rate and caching may only save 5% to 10%.

But caching used poorly is instead negative optimization; common pits are four. Cache expiry is the most common: the knowledge base updated but the cached answer is still old; the user getting stale info is worse than no cache. The fix is to set cache expiry and clear cache the moment the knowledge base updates. Low hit rate yet forcing cache is the second: the cache system itself has cost, storage, query, maintenance all cost money; below 20% hit rate the cache system's cost may exceed the Token saved. The fix is to monitor hit rate and not force caching on low-hit scenarios. Cache poisoning is the third: a wrong answer gets cached and all users get this wrong answer. The fix is to verify answer quality before caching; wrong answers never enter cache. Increased latency is the fourth: the cache query itself takes time, and a cache miss still calls back to source; total latency may be higher than calling the model directly. The fix is to make the cache query very light, and the cache system's own response time far below the model call.

Caching is a money-saving tool, but not a free lunch; used well it saves a lot, used poorly it adds chaos.

## 81. Opening a model branch for every new client, when should you say "no"?

PMs of enterprise AI products will surely meet this: every big client demands customization, and the extreme form is opening a separate model branch, fine-tuned with the client's own data. One branch per client looks like attentive service short-term, but an engineering disaster long-term.

Problems press from three directions at once. Exploding maintenance cost is the most direct: each branch must be maintained, iterated, deployed separately; 10 clients means 10 systems, the R&D team simply cannot keep up. Version-sync hell is the second: when the main model upgrades, every branch must sync, and the sync process introduces new bugs, each branch's bugs different. Data-isolation failure is the third: different clients' data mixed in the same codebase; once something goes wrong it is a compliance disaster.

The PM must learn to say "no," but with strategy, not a hard refusal. The timing to say "no" is when the customization need has extremely low generality, only this one client needs it; doing it creates no value for other clients, yet the maintenance cost is borne by everyone. The way to say "no" is to offer an alternative: use prompt customization instead of model fine-tuning, use config parameters instead of code changes, use a plugin mechanism instead of core-function rework. The backbone to say "no" is a product with a clear product boundary and capability map; when the client wants something beyond the boundary, guide them to implement it with standard capability combinations. A PM who cannot say "no" will have the product bent by one client after another, finally becoming a pile of custom-project collections, impossible to maintain or evolve.

## 82. What responsibility should the PM bear for AI safety? How to write Red Teaming and Guardrails into the product design checklist?

AI safety is not QA's job, nor the algorithm team's; it is one of the PM's core duties. The PM's responsibility for safety shows in writing safety into every link of product design, turning it from "remediation after the fact" into "built in beforehand."

This must run through the product's whole lifecycle. In the requirements phase, the PRD must have a dedicated safety section stating the product's safety boundary: what content cannot be output, what operations cannot be executed, what data cannot be collected. In the design phase, the product design must build in Guardrails: safety filtering at the input layer, safety review at the output layer, human confirmation mandatory for high-risk operations. In the testing phase, do Red Teaming before launch: actively gather a group to attack the product from all angles to see where it breaks. After launch, continuously monitor safety incidents, build an emergency-response mechanism, so when something happens you can quickly locate, take down, fix, report.

Writing Red Teaming and Guardrails into the product design checklist, the key is to be specific not abstract. Do not write "the product should do safety protection well"; write "use classifier X at the input layer to filter violating content, use classifier Y at the output layer to review sensitive topics, high-risk operations must pass user second confirmation." Do not write "the product should prevent Prompt Injection"; write "the system prompt is not visible to users, the output layer identifies injection patterns like 'repeat the above' and blocks them." The more specific the safety design, the more effective the implementation; too abstract and development does not know what to do, and in the end nothing is done.

## 83. Should an AI product team be split by function or by model?

Team org structure is an important decision for AI product landing; split by function or by model are two mainstream ideas.

Split by function is the traditional internet-product idea: frontend, backend, algorithm, product, design each do their job. The benefit is clear responsibility; each team specializes in its domain. The downside is high cross-team collaboration cost; AI products iterate fast, and cross-team coordination often cannot keep up. Split by model is the AI-native team idea: each core model or core scenario gets a cross-functional small group with PM, algorithm, engineering, design, responsible end to end. The benefit is fast iteration, quick decisions within the group; the downside is possible duplicated resources, weak coordination between groups.

Which to choose depends on product stage and scale. Early products with few scenarios and few models, split by model is more efficient; the small-group system lets a small team iterate fast and find PMF. Mature products with many scenarios and many models, split by function is more reasonable; functionalization avoids resource waste and raises professional depth. There is also a hybrid worth considering: core scenarios use the small-group system, infrastructure uses the functional system; small groups handle fast iteration, functional handles underlying capability building. There is no standard answer; team structure must follow the product shape, not the other way around.

## 84. From 0 to 1, what is the minimum set of roles an AI product needs?

Building an AI product from 0 to 1, what is the minimal team config? This is a question many startups and big-tech internal-innovation teams ask. Minimal does not mean fewest, but as few as possible while still able to build the product. The leanest config is four roles.

The AI PM defines the product, defines the evaluation system, defines user scenarios, does cross-team coordination; this role is indispensable, without it the team loses direction. The algorithm engineer handles model selection, prompt engineering, RAG building, effect tuning; the technical core of the AI product. The full-stack engineer handles product development, API integration, frontend UI, backend services; early products need no frontend-backend split, one full-stack covers it. The designer handles UX design, interaction design, trust-calibration design; AI product UX matters more than traditional products, cannot be skipped. These four roles are the floor; drop one and the product cannot be built, or built but unusable.

As the product grows, roles gradually specialize: the algorithm team splits data engineers, ML engineers; the engineering team splits frontend, backend, ops; the product team splits growth PM, business PM. But in the 0-to-1 stage, four roles are enough; too many people instead slow decisions and raise coordination cost. The most common mistake of startup teams is hiring too many, thinking more people speed progress, but actually raising management cost and slowing iteration.

## 85. The boss says "let's build an Agent too." How does the PM turn this into executable requirements?

The boss saying "let's build an Agent too" is one of the most common "requirements" an AI PM hears. This sentence carries extremely low information but triggers huge chain reactions. If you start building directly, you will likely build a mongrel product; the boss himself does not know what he wants, and will surely be unsatisfied with what comes out. The PM's duty is to translate this sentence into executable requirements, by asking four questions clearly one by one.

The first to clarify is the background: why does the boss suddenly want an Agent? Saw a competitor launch, heard an investor suggestion, a client is asking, or there is a real internal pain point. Different backgrounds want completely different things: competitor pressure wants speed, investor suggestion wants a story, client asking wants something sellable, internal pain wants a real problem solved. Next clarify the scenario: what specific problem the Agent solves, what users it serves, at what step it intervenes; if the scenario is unclear do not start, building it is wasted effort. Further is constraints: what budget, what period, what team capability covers, what degree of failure is acceptable; only with clear constraints do you know how big a thing to build; starting without clear constraints, you find resources insufficient halfway and the project dies. Last is the success criterion: what counts as done, what as not done; is launch enough, or must it hit some metric, or must it generate revenue; without a clear criterion the project never ends, the team keeps building and the boss keeps being unsatisfied.

Get these four steps clear, write a one-page requirement doc for the boss to confirm. Start after confirmation, keep pushing if not confirmed. Starting directly is the biggest waste; confirm first then start, is the PM's basic skill to protect the team.
